The Rector Assignment OS is the first SBS University AI OS vertical to complete the full validated build chain:

- **Backend**: models, services, API routes, lifecycle hooks, SLA/escalation engine
- **Frontend**: role-based UI, SLA badges, outbox timelines, dashboard analytics, audit trails

- controlled seed data for onboarding pilot users
- defined assignment templates for institutional use cases
- default SLA and escalation policies

This prevents a "built but not deployed" dead-end and establishes the rollout discipline for future verticals.

## 15. Rollback Plan

### Rollback Conditions
- P1 security incident (tenant leakage, unauthorized access)
- Critical data corruption
- Unrecoverable workflow blocker affecting > 50% of pilot users
- Explicit Pilot Owner instruction

### Rollback Steps (ordered)

1. **Stop new assignment creation**: disable create-assignment route permission for pilot tenant (no table drop)
2. **Notify pilot users**: inform of temporary suspension with estimated resolution
3. **Preserve audit data**: do NOT delete audit logs or assignment history
4. **Export pilot data**: run data export if requested (assignments, reports, audit events)
5. **Archive assignments**: set pilot assignments to `ARCHIVED` status — no hard delete
6. **Disable route access**: remove pilot user roles via admin panel — do not drop tables
7. **Notify Technical Owner**: confirm rollback state
8. **Root cause analysis**: document incident in pilot log before re-activation
9. **Reactivation**: only with Pilot Owner explicit approval

### What is NEVER done in rollback
- No `DROP TABLE`
- No hard delete of assignments, reports, or audit logs
- No destructive migration
- No rollback without explicit Pilot Owner approval
- No silent permission override
