## 10. Database Schema

### Design Principles
- All tables prefixed `rector_`
- Every table has `tenant_id` (BigInteger, NOT NULL, indexed)
- Primary keys: `BigInteger` autoincrement (consistent with `academic_records` pattern)
- Enums: PostgreSQL `ENUM` type or `VARCHAR(64) + CHECK CONSTRAINT` — use `VARCHAR(64)` with Python-side enum for portability, consistent with existing modules using `String(64)` for status
- Timestamps: `TIMESTAMP WITH TIME ZONE` (timezone-aware)
- No hard delete: archive pattern only
- All FK queries must include `tenant_id` filter

## 11. Status Lifecycle and Transition Matrix

### Status Definitions

| Status | Meaning |
|--------|---------|
| `DRAFT` | Created, not yet published/assigned |
| `ASSIGNED` | Published and routed to assignee |
| `ACCEPTED` | Executor acknowledged and accepted |
| `IN_PROGRESS` | Active execution underway |
| `REPORT_SUBMITTED` | Executor submitted progress report; awaiting review |
| `RETURNED_FOR_REVISION` | Reviewer returned report; needs resubmission |
| `COMPLETED` | Reviewer marked done; officially closed |
| `OVERDUE` | Past due_date without COMPLETED (computed, not manually set) |
| `ESCALATED` | Triggered by overdue policy or manual escalation |
| `CANCELLED` | Officially cancelled with reason; not hard deleted |
| `ARCHIVED` | Long-term storage; read-only |

### Allowed Transitions

| From | To | Required Permission | Required Reason | Audit Event |
|------|----|--------------------|-----------------|-----------  |
| *(none)* | `DRAFT` | create | — | ASSIGNMENT_CREATED |
| `DRAFT` | `ASSIGNED` | assign | — | ASSIGNMENT_ASSIGNED |
| `DRAFT` | `CANCELLED` | cancel | ✅ | ASSIGNMENT_CANCELLED |
| `ASSIGNED` | `ACCEPTED` | accept (+ assignee check) | — | ASSIGNMENT_ACCEPTED |
| `ASSIGNED` | `CANCELLED` | cancel | ✅ | ASSIGNMENT_CANCELLED |
| `ASSIGNED` | `OVERDUE` | *(system only)* | — | ASSIGNMENT_OVERDUE_MARKED |
| `ACCEPTED` | `IN_PROGRESS` | status.change or implicit | — | ASSIGNMENT_UPDATED |
| `ACCEPTED` | `REPORT_SUBMITTED` | report.submit | — | REPORT_SUBMITTED |
| `ACCEPTED` | `OVERDUE` | *(system only)* | — | ASSIGNMENT_OVERDUE_MARKED |
| `IN_PROGRESS` | `REPORT_SUBMITTED` | report.submit | — | REPORT_SUBMITTED |
| `IN_PROGRESS` | `OVERDUE` | *(system only)* | — | ASSIGNMENT_OVERDUE_MARKED |
| `REPORT_SUBMITTED` | `RETURNED_FOR_REVISION` | return | ✅ | RETURNED_FOR_REVISION |
| `REPORT_SUBMITTED` | `COMPLETED` | complete | — | ASSIGNMENT_COMPLETED |
| `RETURNED_FOR_REVISION` | `IN_PROGRESS` | status.change (executor) | — | ASSIGNMENT_UPDATED |
| `RETURNED_FOR_REVISION` | `REPORT_SUBMITTED` | report.submit | — | REPORT_SUBMITTED |
| `OVERDUE` | `ESCALATED` | escalate | ✅ | ASSIGNMENT_ESCALATED |
| `OVERDUE` | `REPORT_SUBMITTED` | report.submit | — | REPORT_SUBMITTED |
| `ESCALATED` | `IN_PROGRESS` | status.change | — | ASSIGNMENT_UPDATED |
| `ESCALATED` | `REPORT_SUBMITTED` | report.submit | — | REPORT_SUBMITTED |
| `ESCALATED` | `COMPLETED` | complete | — | ASSIGNMENT_COMPLETED |
| `COMPLETED` | `ARCHIVED` | archive | — | ASSIGNMENT_ARCHIVED |
| `CANCELLED` | `ARCHIVED` | archive | — | ASSIGNMENT_ARCHIVED |

### Forbidden Transitions (enforced in service, return HTTP 409)

| Rule | Description |
|------|-------------|
| `* → DRAFT` | DRAFT is only an initial create state; no re-draft |
| `COMPLETED → *` | COMPLETED is terminal; no reversal (except ARCHIVED) |
| `ARCHIVED → *` | ARCHIVED is immutable |
| `CANCELLED → active status` | Cancelled cannot be reactivated |
| Executor → COMPLETED | EXECUTOR role cannot set COMPLETED; requires RECTOR/VICE_RECTOR/CONTROLLER |
| System → COMPLETED | No autonomous completion without human actor permission |
| Hard delete | No hard delete of any assignment or report |

### OVERDUE Computation Rule

```
OVERDUE is not a manual status.
It is COMPUTED when:
  assignment.status IN ('ASSIGNED', 'ACCEPTED', 'IN_PROGRESS')
  AND assignment.due_date IS NOT NULL
  AND assignment.due_date < CURRENT_DATE

The overdue detection runs as:
  1. Background scheduled job (cron/scheduler) — deferred to A-031.5
  2. On-demand during dashboard summary computation (A-031.1 scope)
  3. On-demand during list query (lazy evaluation option)

OVERDUE is NEVER manually set by a user.
Dashboard overdue_count reflects real computed value, not a stored field.
```

### Every Transition Invariants

1. Validate `tenant_id` from auth claims (fail-closed)
2. Validate actor permission using `permission_dependency`
3. Validate current status allows requested transition
4. Write `rector_assignment_status_history` row (INSERT, never UPDATE)
5. Write `rector_assignment_audit_events` row (INSERT, never UPDATE)
6. Propagate `request_id` from `request.state` if available
7. Update `rector_assignments.updated_at` and relevant timestamp field

## 14. Service Layer Contract

All service functions in `backend/app/modules/rector_assignment_workflow/service.py`.

1. `tenant_id` parameter: validated via `validate_tenant_id_provided(tenant_id)` from `app.core.module_helpers.service_validation`

## 17. Tenant / Security / RBAC / ABAC Rules

### Tenant Fail-Closed

1. `tenant_id` is ALWAYS extracted from authenticated token claims via `get_current_tenant` dependency
2. `X-Tenant-ID` header is a consistency check only; mismatch raises HTTP 403 (except superadmin on non-dashboard paths — follows `core/tenant.py`)
3. `tenant_id` from request body is IGNORED for security purposes
4. Every DB query includes `WHERE tenant_id = :tenant_id`
5. All child entity queries include parent assignment tenant check:
   - `report.tenant_id == assignment.tenant_id`
   - `escalation.tenant_id == assignment.tenant_id`
   - Cross-module: `source_decree_id` is a soft FK; no automatic join to external module tables
6. Invalid tenant → 403; missing tenant → 401; inactive tenant → 403; not found → 404

### RBAC

1. Every route uses `Depends(permission_dependency("admin.rector_assignments.X"))` where X matches permission table in §8
2. `permission_dependency` from `app.modules.rbac.security` validates the authenticated user has the required permission in their resolved role set for the tenant
3. Permission failures return HTTP 403

### ABAC Rules (service layer enforcement)

| Rule | Check | Failure |
|------|-------|---------|
| Executor can only submit report on own assignment | `SELECT 1 FROM rector_assignment_assignees WHERE assignment_id=? AND user_id=? AND tenant_id=?` | `DomainValidationError("not assigned to this assignment")` → router maps to 403 |
| Director scoped to department | `actor_roles includes DIRECTOR AND responsible_unit_id = actor_unit_id` | `DomainValidationError` → 403 |
| Executor cannot COMPLETE | Check `actor_role NOT IN [RECTOR, VICE_RECTOR, CONTROLLER]` before complete | `DomainValidationError("executor role cannot complete assignment")` → 403 |
| INTERNAL comments not visible to EXECUTOR | Filter in `list_comments` query: `WHERE visibility != 'INTERNAL' OR actor_role IN (RECTOR, VICE_RECTOR, CONTROLLER, PLATFORM_ADMIN)` | Filter (no error) |
| PLATFORM_ADMIN is still tenant-scoped | `platform_admin` cannot access other tenants without `superadmin` + valid X-Tenant-ID | 403 |

### Security Boundaries

| Threat | Mitigation |
|--------|-----------|
| IDOR (Insecure Direct Object Reference) | All queries include `tenant_id` filter; `assert_resource_belongs_to_tenant` from `service_validation.py` |
| SQL injection | SQLAlchemy parameterized queries only; no raw f-string SQL |
| Privilege escalation | Role not writable by user; managed by PLATFORM_ADMIN; `originator_role` is a snapshot string, not live role check |
| Evidence URL injection | `url` validated as HTTPS only; `HttpUrl` Pydantic validator |
| Body-based tenant override | `tenant_id` from body fields (if present) is IGNORED; auth claims are sole source |
| CSRF | Cookie auth + SameSite; CSRF middleware already in FastAPI app stack |
| Audit log tampering | `rector_assignment_audit_events` is INSERT-only in service layer; no UPDATE/DELETE methods exposed |

## 19. Dashboard Summary Contract

### Anti-Fake Requirement

The `get_dashboard_summary` service function **must**:
1. Execute real SQL queries against `rector_assignments`, `rector_assignment_reports`, `rector_assignment_escalations`
2. Never use hardcoded values for any count field
3. Compute `overdue_count` as: `COUNT(*) WHERE status IN ('ASSIGNED','ACCEPTED','IN_PROGRESS','RETURNED_FOR_REVISION') AND due_date IS NOT NULL AND due_date < CURRENT_DATE AND tenant_id = ?`
4. Return `fake_metrics: False` always (literal `False`, not computed)
5. Return `data_source: "computed_from_assignments"` always

### Expected Queries in `get_dashboard_summary`

```sql
-- 1. Status counts
SELECT status, COUNT(*) as cnt
FROM rector_assignments
WHERE tenant_id = :tenant_id AND is_archived = FALSE
GROUP BY status;

-- 2. Overdue count (active + past due)
SELECT COUNT(*) FROM rector_assignments
WHERE tenant_id = :tenant_id
  AND status IN ('ASSIGNED', 'ACCEPTED', 'IN_PROGRESS', 'RETURNED_FOR_REVISION')
  AND due_date IS NOT NULL
  AND due_date < CURRENT_DATE
  AND is_archived = FALSE;

-- 3. Due this week
SELECT COUNT(*) FROM rector_assignments
WHERE tenant_id = :tenant_id
  AND status NOT IN ('COMPLETED', 'CANCELLED', 'ARCHIVED')
  AND due_date BETWEEN CURRENT_DATE AND CURRENT_DATE + INTERVAL '7 days';

-- 4. By unit
SELECT responsible_unit_id, COUNT(*) FROM rector_assignments
WHERE tenant_id = :tenant_id AND is_archived = FALSE
GROUP BY responsible_unit_id;

-- 5. Completion rate (last 30 days)
SELECT COUNT(*) FROM rector_assignments
WHERE tenant_id = :tenant_id
  AND status = 'COMPLETED'
  AND completed_at >= CURRENT_TIMESTAMP - INTERVAL '30 days';

-- 6. Average days to complete
SELECT AVG(EXTRACT(EPOCH FROM (completed_at - created_at)) / 86400)
FROM rector_assignments
WHERE tenant_id = :tenant_id AND status = 'COMPLETED' AND completed_at IS NOT NULL;
```
