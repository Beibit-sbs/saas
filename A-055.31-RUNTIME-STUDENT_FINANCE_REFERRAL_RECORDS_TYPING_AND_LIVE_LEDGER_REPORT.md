# A-055.31 Runtime - Student-Finance Referral Records Typing and Live Ledger Report

## Scope

Close the frontend/backend contract gap found in A-055.30: the bridge endpoint
returns `records[]` but the frontend type dropped them. Type the records and
make the acknowledgement ledger render them live.

```text
backend records[] -> typed frontend records -> live read-only acknowledgement rows
```

## Result

- Frontend types: added `FpaMetadataRecord` (mirrors backend
  `schemas.FpaMetadataRecord`: id, tenant_id, status, reference_key, title,
  source_module, source_record_id, metadata, limitations, created_at) and
  `FpaBridgeRecordsResponse { records: FpaMetadataRecord[] }`.
- API: `getFpaBridgeStudentFinanceReferrals` return type corrected from the
  records-less `FpaBridgeSummary` to `FpaBridgeRecordsResponse` (honest typing
  of what `GET /bridges/student-finance-referrals` actually returns).
- Component: extracted `FpaStudentFinanceReferralAcknowledgementLedger({ records })`.
  When records with `metadata.acknowledgement_state` exist it renders a
  read-only row per acknowledgement (acknowledgement_state, referred_by_user_id,
  source_hardship_id, referral_target); when empty it shows the declarative
  contract fallback (preserving the A-055.30 surface).

## Safety Boundaries

Read-only. No aid approval, payment execution, billing balance mutation, or ERP
posting is exposed.

## Contract Updates

- No backend change. Route count `57`, permission count `51`, table count `24` unchanged.
- Frontend type now honestly reflects the backend `FpaBridgeResponse`
  (`FpaCollectionResponse.records`).

## Known limitation (honest)

The ledger is now render-capable and typed, but the finance frontend module is
still a metadata-shell with **no data-fetch layer** (no hooks, the api client is
never called in-module). So in the live app the page renders the ledger with an
empty record set (declarative fallback); the live rows are exercised by tests
and will display real data only once a data-fetch path (react-query hook) is
added for the module — a module-wide architecture decision, intentionally not
made in this node.
