## 5. Frontend Architecture Findings

### Framework
- Next.js App Router (`frontend/app/`)
- Route groups: `(admin)`, `(auth)`, plus top-level `faculty`, `student`, `registrar`
- Admin portal: `frontend/app/(admin)/console/...`

### State Management
- TanStack Query (`@tanstack/react-query`)
- `useQuery` for reads, `useMutation` for writes
- `useQueryClient` + `invalidateQueries` after mutations
- `staleTime`: 60000ms for lists/dashboard, 30000ms for detail views

### API Client Pattern
- Client: `frontend/shared/api/client.ts` exports `apiGet`, `apiPost`, `apiPut`, `apiPatch`, `apiDelete`
- All calls use `credentials: "include"` (cookie-based auth)
- Path rewriting: `mapToBffPath()` routes `/api/admin/...` → `/api/bff/admin/...`
- BFF proxy: `frontend/app/api/bff/[...path]/route.ts` → `proxyBffRequest()`
- BFF reads `app_access_token` or `admin_token` cookie → injects `Authorization: Bearer {token}` header
- BFF upstream timeout: 8000ms
- Error handling: `ApiRequestError` with `.status` and `.code`, emits `sessionInvalid` on 401

### BFF Upstream Path Resolution
For `/api/bff/admin/rector-assignments/...`:
```
toUpstreamPath(["admin", "rector-assignments", ...]) → /api/admin/rector-assignments/...
```
Backend path: `GET /api/admin/rector-assignments` → upstream URL: `{API_BASE}/api/admin/rector-assignments`

No custom BFF route needed for rector-assignments — the catch-all `/api/bff/[...path]/route.ts` handles all methods.

### Permission System
- Constants in `frontend/shared/config/permissions.ts`
- Pattern: `PERMISSION_KEY: "admin.module.action"` 
- Component: `RequirePermission permission={PERMISSIONS.KEY}` from `@/shared/auth/permission-gate`
- Hook: `usePermissions()` from `@/shared/hooks/use-permissions` for conditional rendering

### Navigation Pattern
- Config: `frontend/shared/config/navigation.ts`
- Structure: groups with `label`, `items[]` (each has `label`, `href`, `icon`, `permission`)
- `AppSidebar` renders groups; items filtered by user permissions
- Rector assignments needs a new nav group or entry in "Operations" group

### Module Pattern
- Location: `frontend/modules/{module-name}/hooks.ts` + `types.ts`
- Hooks file: named exports for `use{Module}{Action}()` following TanStack Query pattern
- Types file: enums + interfaces for domain entities

## 6. Selected Frontend Strategy

**Strategy: ADMIN_CONSOLE_EXPANSION** — Extend existing admin console pattern with rector-assignments module.

Rationale:
- Backend permissions are all `admin.rector_assignments.*` (admin-scoped)
- Executor and Rector/Controller views both live in admin console with role filtering
- All requests flow through BFF catch-all proxy (no new BFF route file needed)
- Consistent with procurement-workflow, scheduling, thesis, and other complex workflow modules
- Executor inbox = filtered list view showing assignments where current user is an assignee

Rejected alternatives:
- SEPARATE_EXECUTOR_PORTAL: not needed; admin portal already supports role-filtered views
- DEDICATED_BFF_ROUTE: not needed; catch-all BFF proxy handles all paths including rector-assignments
- DIRECT_API_CALL: not allowed by project pattern; all calls must go through BFF

## 8. Role-Based UX

### Rector / Vice Rector

Entry point: `/console/rector-assignments`

Capabilities:
- Executive KPI cards: active/overdue/escalated/completed/total counts
- Create assignment (if `admin.rector_assignments.assignment.create`)
- Review submitted reports + return/complete actions
- View audit trail for any assignment
- View full evidence timeline
- Filter by unit, status, priority, due date
- Escalate assignments (if `admin.rector_assignments.assignment.escalate`)

Hidden from Rector: template management (unless also Admin)

### Controller / Secretary

Entry point: `/console/rector-assignments`

Capabilities:
- Full registry view + monitoring dashboard
- Draft creation + template selection
- Overdue board at `/console/rector-assignments/overdue`
- Escalation queue at `/console/rector-assignments/escalations`
- Report review queue (return/complete actions)
- Comment and evidence review
- Audit viewer

Hidden from Controller: direct assignment completion without review (backend enforces)

### Executor

Entry point: `/console/my-assignments`

Capabilities:
- My assignments inbox (filtered to `my_assignments=true` query param or user_id filter)
- Accept assignment (if status=ASSIGNED and user is assignee)
- Submit progress report (if assigned + eligible status)
- Attach evidence metadata
- Respond to revision requests
- Add comments
- View deadline/status timeline

Hidden from Executor: assignment creation, other users' assignments, templates, full registry

### Director / Dean

Entry point: `/console/rector-assignments` (filtered to their unit)

Capabilities:
- Unit-scoped registry (filter `unit_id={director_unit_id}`)
- Review reports within unit
- Assign internal co-executors (if `admin.rector_assignments.assignment.assign`)
- Monitor unit overdue tasks

### Auditor / Observer

Entry point: `/console/rector-assignments`

Capabilities:
- Read-only registry (all statuses visible)
- Audit trail view at `/console/rector-assignments/[id]/audit`
- Evidence timeline (view only)
- No create, no transition, no comment actions

All mutation buttons hidden (frontend hiding = UX only; backend enforces).

### Platform Admin

Entry point: `/console/rector-assignments/templates`

Capabilities:
- Full template CRUD
- Role/permission visibility (via RBAC module)
- No cross-tenant bypass
