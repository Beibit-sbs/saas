## 1. Objective

Wire all 12 Wave 1 KPI metrics (from A-013.5) into the 3 relevant admin console pages so operators can see them inline without navigating to a separate KPI dashboard. Changes are strictly additive — no new libraries, no new dashboard framework, no page rewrites.

---

## 2. Architecture Decisions

### 2.1 Dynamic Card Rendering (Executive Dashboard)
The main dashboard page (`console/dashboard/page.tsx`) already maps `data.cards` to `KpiCard` components dynamically. Because the backend already returns Wave 1 cards from the KPI refresh service, **no structural change** was required to the dashboard grid — it simply renders new cards automatically.

The only dashboard change needed was **visual severity differentiation** — Wave 1 KPIs with threshold violations need a colored left border to draw operator attention.

### 2.2 New Component: `Wave1KpiBar`
A lightweight `Wave1KpiBar` component was created to surface relevant KPI metrics inline on each feature page. It:
- Calls `useTenantKpiMetrics()` (existing hook) to fetch live metrics
- Accepts `metricKeys` and `labels` props — no backend contract coupling
- Shows a skeleton loader while fetching; disappears if data is null
- Reads `user.tenantId` from `useAdminAuth()` — same auth pattern as `InterventionsSummaryStats`
- No new libraries, no new endpoints

### 2.3 Reuse Principle
All components reuse existing primitives: `Skeleton`, `useAdminAuth`, `useTenantKpiMetrics`. No new hooks were written.

## 5. Component Design: `Wave1KpiBar`

```tsx
interface Wave1KpiBarProps {
  metricKeys: string[];
  labels: Record<string, string>;
}
```

- Renders as a `flex flex-wrap gap-3` row of chips
- Each chip: `rounded-md border bg-muted/30 px-3 py-2` — consistent with existing `Card` visual language
- Empty/missing values: shows `—` (em-dash)
- `data-testid="wave1-kpi-bar"` for test targeting
- `data-testid="wave1-kpi-bar-loading"` for skeleton state

## 6. `KpiCard` Severity Enhancement

```tsx
// Before
<Card>

// After
<Card
  className={cn(
    severityLevel === "critical" && "border-l-4 border-l-rose-500",
    severityLevel === "warning" && "border-l-4 border-l-amber-500",
  )}
>
```

The `severityLevel` value is read from `card.metadata_json.severity_level`, which is populated by the backend `KPI_SEVERITY_RULES` evaluation in `kpi/service.py`.
