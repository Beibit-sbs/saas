## 1.1 Что это за проект

**SBS UB** — полностековая **мультитенантная SaaS‑платформа управления университетом** (University Operating System). Система объединяет административные, академические, финансовые, кадровые, кампусные и исследовательские процессы вуза в единую платформу с централизованным «мозгом» (**Brain Core**), который анализирует межмодульный контекст и формирует управленческие рекомендации/решения под контролем человека.

### Противоречие в идентичности продукта (зафиксировано, не разрешено)

| Источник | Позиционирование |
|----------|------------------|
| `README.md` | «AI Engineering Center» — **доменно‑нейтральный шаблон платформы**; высшее образование — лишь один из примеров профиля адаптации |
| `frontend/app/login` (UI) | «AI University Console» |
| `SBS_UB_PROJECT_CONTEXT_2026.md`, `SBS_UB_*` | **Университетская управляющая платформа** (University OS), 241 backend модуль |

**Вывод аудита:** фактический код (241 модуль с университетскими доменами — admissions, enrollments, faculty, research, accreditation и т.д.) однозначно реализует **University OS**. Формулировка «шаблон платформы» в `README.md` — это позиционирование ядра как переиспользуемого, но доменное наполнение — университетское.

## 1.2 Для чего создан проект

- Предоставить вузу **единую операционную систему** вместо разрозненных систем (СДО, деканат, бухгалтерия, HR, кампус).
- Автоматизировать **сквозные процессы жизненного цикла студента** (от приёмной кампании до выпуска и alumni).
- Обеспечить **раннее предупреждение рисков** (успеваемость, посещаемость, финансы, аккредитация, безопасность) через Brain Core.
- Дать руководству вуза **исполнительные дашборды и KPI** (Rector / Executive Control Tower) и **отчётность для министерства** (Ministry / NOBD / рейтинги).
- Соответствовать **регуляторным и аккредитационным требованиям** с прослеживаемостью доказательств (evidence lineage).

## 1.4 Основные сценарии использования

1. **Полный академический жизненный цикл** (реализован как «runtime‑дерево» A‑055): онбординг тенанта‑админа → оргструктура → программы/курсы → зачисление → секции/расписание → занятия → посещаемость → оценки → транскрипт/GPA → прогресс по программе → выпуск → alumni → финансовый мост студента → hardship‑поддержка.
2. **Приёмная кампания:** абитуриент → заявление → этапы workflow → документы → скоринг → решение (accept/reject/waitlist).
3. **Раннее предупреждение и интервенция:** событие риска (посещаемость/оценки/финансы) → Brain Core → решение → создание intervention‑case → уведомление advisor/faculty → отслеживание исхода.
4. **Утверждение изменения расписания человеком:** предложение → симуляция «what‑if» → очередь утверждения → решение человека → ручное применение.
5. **Governance:** Rector/исполком видит cross‑domain risk heatmap, KPI drill‑down с доказательствами, очередь governance‑алертов, поручения с SLA.
6. **Регуляторная отчётность:** сбор данных → готовность отчёта (Ministry/NOBD/ranking) → аудит доставки.

Подробные пошаговые сценарии: [08_WORKFLOWS.md](08_WORKFLOWS.md).

## 1.5 Пользователи (роли)

Система ролевая (RBAC + ABAC). Ключевые категории пользователей:

- **Платформенные:** `superadmin`, `platform_admin` (управление тенантами, флагами, биллингом, здоровьем платформы).
- **Аудит/контроль:** `auditor` (read‑only по всем доменам + audit‑лог).
- **Руководство вуза:** `rector`, `executive_control_tower` (дашборды, поручения, стратегия).
- **Административные доменные роли:** `student_lifecycle_admin`, `academic_operations_admin`, `research_science_admin`, `quality_accreditation_admin`, `finance_procurement_asset_admin`, `security_access_compliance_admin`, `student_services_support_admin` и др.
- **Функциональные:** registrar, faculty (преподаватель), advisor, finance officer, HR, security officer.
- **Конечные пользователи:** `student` (портал студента), faculty‑портал, registrar‑портал.

Полный аудит ролей: [03_ROLES_AND_RBAC.md](03_ROLES_AND_RBAC.md).

> **Оговорка о зрелости UI:** по `README.md`, админ‑консоль значительно глубже проработана, чем ролевые порталы конечных пользователей (`/student`, `/faculty`, `/registrar` присутствуют, но не как полные production‑журнеи).

## 1.6 Типы организаций, использующих систему

- **Высшие учебные заведения** (основной целевой профиль): университеты, институты — мультитенантно (каждый вуз = отдельный `tenant`).
- Заявленные в `README.md` как потенциальные профили адаптации ядра: внутренние enterprise‑инструменты, регулируемые административные системы, AI‑сервисы. **Фактическое доменное наполнение — университетское.**
- Регуляторный контекст: присутствуют адаптеры и отчётность под **Казахстан (KZ)** (NOBD, министерство), с заявленными планами адаптеров для SA/AE/QA/OM/BH/KW (см. [09_INTEGRATIONS.md](09_INTEGRATIONS.md)).

## 1.7 Автоматизируемые бизнес‑процессы (сводно)

- Приём и зачисление, движение по этапам, решения.
- Формирование расписания, разрешение конфликтов, рекомендации по аудиториям, утверждение человеком.
- Мониторинг посещаемости/успеваемости → авто‑создание интервенций.
- Финансовые процессы: бюджеты, закупки (approval → PO → поставка → актив), задолженности, сверка платежей.
- Кадровые: найм, онбординг, аттестация, офбординг, payroll.
- Кампусные: work orders, бронирование аудиторий/оборудования, посетители, доступ.
- Исследовательские: заявки на этику, гранты, публикации, IP.
- Качество/аккредитация: циклы самооценки, сбор доказательств, корректирующие действия.
- Документооборот: приказы/декреты, корреспонденция, ЭЦП, архив, SLA.
- Governance/отчётность: поручения, KPI, регуляторные отчёты.

Каждый процесс детализирован в [08_WORKFLOWS.md](08_WORKFLOWS.md) и в файлах [modules/](modules/).
