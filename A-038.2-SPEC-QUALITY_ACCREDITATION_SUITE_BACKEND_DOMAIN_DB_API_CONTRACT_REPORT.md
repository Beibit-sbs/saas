# A-038.2-SPEC - Quality / Accreditation Suite Backend Domain / DB / API Contract Report

## 1. Executive Summary

A-038.2-SPEC defines the backend domain, database, API, permissions, schema, repository, service, evidence, dashboard, bridge, migration, validation, and test contract for the future Quality / Accreditation Suite backend foundation. This action is backend-contract specification only and docs-only. No backend runtime, migrations, models, schemas, repositories, services, routers, tests, frontend runtime, Playwright specs, provider integrations, or real accreditation data were created or changed in this action.

The backend strategy remains one controlled module at `backend/app/modules/quality_accreditation/` with bounded subdomains, not one backend package per capability row. The contract uses `qa_` database tables, tenant fail-closed behavior, explicit RBAC permissions, metadata-and-evidence-only defaults, append-only audit and status history, read-only-first bridge records, deterministic readiness metadata, and anti-fake boundaries that forbid official accreditation approval, official ministry submission, ranking claims, fake evidence, fake scores, hidden scores, provider sync, external database sync, and autonomous accreditation decisions.

## 10. Service Contract

Service responsibilities:

- validate tenant fail-closed
- reject invalid tenant IDs: `None`, `0`, negative, bool, float, string
- enforce `human_review_required=true`
- enforce all official/provider/autonomy/fake/hidden-score flags false
- create audit events on create/update/review actions
- create status history where status changes
- compute dashboard metadata summaries
- compute gap/readiness metadata only
- compute evidence completeness bands without fake KPI or hidden score
- return limitations and `incomplete_data` clearly
- provide read-only-first bridge summaries

Forbidden service behavior:

- approve accreditation officially
- submit to ministry
- claim official ranking improvement
- create fake evidence
- create fake quality score
- create fake survey result
- calculate hidden program/faculty/student score
- apply autonomous sanction
- automatically close a program
- call provider or external database
- sync accreditation systems
- generate production, sales, GCC, or L5/L6 claims

Readiness / gap logic rules:

- deterministic
- evidence-backed
- explainable
- human-review-gated
- not a hidden score
- surfaced as `readiness_status`, `gap_band`, `missing_evidence`, and `recommended_next_step`
