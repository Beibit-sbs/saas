## domain_model

Academic Operations Brain covers eighteen canonical domains.

### Domain 1 — Academic Registry

- ownership: academic_operations (canonical owner)
- responsibilities: student cohort classification, academic group taxonomy, advisor/tutor assignment registry, summer-semester term registry, retake plan registry
- producers: academic_operations backend module
- consumers: student_success_runtime, quality_accreditation, executive_governance (via bridge)
- boundaries: metadata-only; no official enrollment decisions, no degree award, no academic policy override

### Domain 2 — Curriculum Management

- ownership: academic_operations (canonical owner); quality_accreditation as supporting bridge consumer
- responsibilities: curriculum structure metadata, course-to-program mapping, curriculum versioning readiness, learning objective alignment
- producers: academic_operations (bridge compositions); curriculum_mapping, program_learning_outcomes (supporting)
- consumers: quality_accreditation (curriculum evidence), student_success_runtime (curriculum risk signals)
- boundaries: metadata-only; no curriculum approval execution, no credit-change automation

### Domain 3 — Course Catalog

- ownership: course_catalog_management (canonical owner); academic_operations as bridge consumer
- responsibilities: course lifecycle metadata (draft/review/approved/archived), course description, syllabus reference, department approval record
- producers: course_catalog_management
- consumers: academic_operations (runtime aggregation), prerequisite_management (dependency input), scheduling (section creation)
- boundaries: no auto-publish, no auto-delete, no auto-credit-change; human review required at publication gate

### Domain 4 — Learning Outcomes

- ownership: course_learning_outcomes (course-level canonical); program_learning_outcomes (program-level canonical); quality_accreditation (accreditation-evidence bridge consumer)
- responsibilities: course learning outcome definitions, program learning outcome definitions, alignment matrix, outcome evidence readiness
- producers: course_learning_outcomes, program_learning_outcomes
- consumers: quality_accreditation (accreditation evidence), academic_operations (aggregate visibility)
- boundaries: no autonomous learning-outcome promotion; outcomes require human review and official curriculum approval path

### Domain 5 — Prerequisite Management

- ownership: prerequisite_management (canonical owner)
- responsibilities: prerequisite rule registry (draft/review/approved/archived), course dependency metadata, exception evidence tracking
- producers: prerequisite_management
- consumers: scheduling (section enrollment gate), academic_operations (curriculum risk view)
- boundaries: no auto-override of student eligibility, no auto-registration; human review required for all exceptions

### Domain 6 — Academic Calendar

- ownership: academic_operations (canonical owner via summer_semester_term registry)
- responsibilities: academic period metadata, semester and term boundaries, summer session windows
- producers: academic_operations
- consumers: scheduling, grades, exam_governance, student_lifecycle, internship
- boundaries: metadata-only; no automated calendar publication; no calendar-driven enrollment trigger

### Domain 7 — Timetable Management

- ownership: scheduling (canonical owner)
- responsibilities: course section creation, schedule assignment, room–section–instructor binding, reschedule and cancellation lifecycle
- producers: scheduling backend module
- consumers: academic_operations (conflict/consistency bridge), student_success_runtime (timetable anomaly indicator), exam_governance (exam window alignment)
- boundaries: schedule changes require scheduling.write permission; no autonomous rescheduling; conflict detection is read-only advisory

### Domain 8 — Classroom Allocation

- ownership: scheduling (canonical owner, through section–room assignment model)
- responsibilities: room assignment to sections, room-schedule view, conflict detection across room–time slots
- producers: scheduling
- consumers: academic_operations (room utilization visibility), facilities_work_orders (bridge)
- boundaries: no autonomous room assignment; no eviction of existing bookings; conflicts are advisory only

### Domain 9 — Teaching Load Management

- ownership: teaching_load_contracts (canonical owner); scheduling (instructor assignment)
- responsibilities: teaching load contract readiness, course assignment evidence, workload policy compliance visibility, faculty-load plan tracking
- producers: teaching_load_contracts (readiness/policy contracts), scheduling (instructor assignments)
- consumers: academic_operations (aggregate load visibility), hr_payroll (load reference via bridge), executive_governance (workload KPI bridge)
- boundaries: no auto-assign teaching load, no auto-change contract, no auto-approve overload; all load decisions require human review

### Domain 10 — Attendance Tracking

- ownership: scheduling (canonical operational owner); attendance service (risk classification utility); academic_operations (brain aggregation consumer)
- responsibilities: lesson attendance records per session, absence/late/excused classification, attendance trend analytics, low-attendance risk threshold compliance
- producers: scheduling (lesson attendance routes), attendance service (risk classification)
- consumers: academic_operations (attendance risk aggregation), student_success_runtime (attendance risk feed), quality_accreditation (attendance evidence bridge)
- boundaries: no automated attendance excuse, no automated disciplinary action; risk classification is advisory; all intervention requires human review

### Domain 11 — Assessment Management

- ownership: grades (operational canonical owner); academic_operations (gradebook metadata canonical owner)
- responsibilities: grade submission lifecycle, grade change workflow, course-level grade aggregation, gradebook structure metadata, grade-enrollment consistency
- producers: grades module (grade transactions), academic_operations (gradebook metadata)
- consumers: academic_operations (grade risk aggregation), student_success_runtime (academic performance feed), quality_accreditation (assessment evidence bridge)
- boundaries: no automated grade calculation, no grade publication without explicit actor, no grade approval automation; official grade actions require grades.write permission

### Domain 12 — Exam Governance

- ownership: exam_governance (canonical owner)
- responsibilities: exam planning (title, term, status), exam grading metadata (average_score, pass_rate), exam statistics and dashboard summary, exam lifecycle (planned/graded/archived)
- producers: exam_governance module
- consumers: academic_operations (exam risk aggregation), student_success_runtime (assessment risk feed), quality_accreditation (exam evidence bridge)
- boundaries: no automated exam scheduling, no automated grading; exam grading endpoint requires exams.write; statistics endpoints are read-only advisory

### Domain 13 — Gradebook Metadata

- ownership: academic_operations (canonical owner of gradebook structure metadata)
- responsibilities: gradebook key registry, gradebook period reference, gradebook structure metadata CRUD
- producers: academic_operations
- consumers: grades (structure reference), academic_operations dashboard
- boundaries: gradebook metadata does not calculate, publish, or approve official grades; no grade aggregation claims

### Domain 14 — Internship Management

- ownership: internship (canonical owner)
- responsibilities: internship posting lifecycle, application FSM (APPLIED/SHORTLISTED/INTERVIEW/OFFERED/ACCEPTED/REJECTED), contract lifecycle (DRAFT/SIGNED/ACTIVE/COMPLETED), industry partner reference
- producers: internship module
- consumers: academic_operations (practicum completion risk aggregation), student_success_runtime (internship completion signal), career_services (bridge consumer)
- boundaries: no automatic offer generation, no automatic contract activation; all lifecycle transitions require explicit actor; completion-without-grade triggers advisory risk only

### Domain 15 — SIS Integration

- ownership: student_information_system_integration (canonical readiness owner)
- responsibilities: SIS provider contract metadata (Platonus/KZ profile), integration readiness classification, configuration evidence tracking, provider boundary controls
- producers: student_information_system_integration
- consumers: academic_operations (integration status visibility), student_lifecycle (data sync boundary reference)
- boundaries: no live Platonus calls, no automated student data sync, no credential storage; provider status claims limited to readiness-contract metadata only

### Domain 16 — LMS Integration

- ownership: learning_management_system_integration (canonical readiness owner)
- responsibilities: LMS provider contract metadata (Moodle/LMS_KZ profile), integration readiness classification, course/grade/attendance sync boundary controls
- producers: learning_management_system_integration
- consumers: academic_operations (LMS status visibility), grades (boundary reference for grade-sync policy)
- boundaries: no live LMS calls, no automated grade sync, no content publication, no credential storage; provider status limited to readiness metadata only

### Domain 17 — Academic Signals

- ownership: brain_core (canonical signal ownership); academic_operations_runtime (signal aggregation and routing)
- responsibilities: academic risk signal inventory, timetable exception signals, curriculum gap signals, attendance threshold breach signals, teaching load overload signals, exam failure rate signals, internship completion risk signals
- producers: brain_core (signal execution), academic_operations (signal aggregation view)
- consumers: student_success_runtime (academic risk feed), quality_accreditation (curriculum signal bridge), executive_governance (executive dashboard bridge)
- boundaries: signals are advisory read-only outputs; no autonomous signal execution; all signal-triggered actions require explicit human actor; no notification dispatch in runtime layer

### Domain 18 — Academic Dashboard

- ownership: academic_operations_runtime (canonical owner of Brain-level aggregated view)
- responsibilities: executive cross-domain KPI aggregation, domain health overview, signal status panel, cross-vertical bridge summary, exception and risk priority view
- producers: academic_operations_runtime (consuming all 17 upstream domains as read-only sources)
- consumers: executive_governance (bridge), reporting_runtime (bridge)
- boundaries: read-only, aggregator-only, no mutation, no approval, no workflow execution; dashboard data is derivative and non-authoritative

- single_canonical_owner rule enforced: no domain has more than one canonical owner

### Cross-Vertical Ownership Boundaries

- Student Success Brain: consumes attendance indicators, academic performance indicators, and risk indicators as read-only bridge inputs; does NOT own any Academic Operations domain

## security_contract

### Mandatory Runtime Standards

- permission_pattern: all runtime GET endpoints require `permission_dependency(SUMMARY_READ)` equivalent scoped to academic_operations domain
- tenant_enforcement: all routes must call `require_academic_operations_tenant` dependency; fail-closed on missing or invalid tenant
- method_restriction: runtime brain endpoints are GET-only; no POST, PATCH, PUT, DELETE in runtime chain
- rbac_namespace: `academic_operations.summary.read` permission slug enforced on all runtime brain routes
- router_isolation: runtime brain routes use dedicated router with `/api/v1/academic-operations/` prefix; not mixed with admin CRUD routes under `/api/admin/academic-operations/`

### Forbidden Runtime Actions

- no_create_operations: runtime routes must not create any database entities
- no_update_operations: runtime routes must not update any database entities
- no_delete_operations: runtime routes must not delete any database entities
- no_workflow_execution: runtime routes must not trigger workflow state changes
- no_approval_execution: runtime routes must not issue approval or rejection decisions
- no_background_processing: runtime routes must not enqueue background jobs or celery tasks
- no_provider_writes: runtime routes must not send data to Platonus, Moodle, or any external system
- no_outbound_integrations: runtime routes must not call external APIs or publish to external event buses
- no_notification_dispatch: runtime routes must not send emails, SMS, push notifications, or other notifications
- no_autonomous_decisions: runtime routes must not make autonomous decisions about students, grades, attendance, or faculty

### Security Inheritance

- inherited from existing academic_operations module: tenant lookup, permission check structure, error normalization helpers
- brain_core signal routing: no live execution; signal consumption is read-only registry query only
- audit trail: all runtime GET requests inherit the existing audit middleware; no separate audit logging required for read-only routes
