## 3 Domain Boundaries

### 3.1 In Scope (Integration / Provider Readiness Suite)

1. Provider Registry and provider canonical metadata.
2. Provider Profile model (capabilities, constraints, required evidence, risk classification).
3. Provider Capability Matrix (by provider type, maturity target, compliance need).
4. Readiness assessment logic and status taxonomy for NON_LIVE_READINESS.
5. Evidence collection model (documents, approvals, audit references, controls).
6. Compliance and security review state tracking.
7. Provider health visibility as readiness-health only (non-live).
8. Provider audit review and traceability.
9. Integration planning artifacts (phase, sequence, dependency map, rollback prerequisites).
10. Provider dashboards and consolidated visibility for governance.

### 3.2 Explicitly Out of Scope (A-046.1-SPEC)

1. Live provider calls.
2. Provider credentials/secrets storage or validation.
3. Provider synchronization (pull/push/event sync).
4. External submissions or external side effects.
5. provider_connected=true status without verified evidence.
6. Real-time provider health telemetry from external systems.
7. Runtime implementation of connectors, SDK clients, queues, jobs, or schedulers.

### 3.3 Product Boundary Rule

Integration / Provider Readiness Suite is a governance and readiness control-plane vertical until explicit runtime authorization in a later action. Any live behavior remains outside this vertical in A-046.1.

## 8 Anti-Fake Boundaries

Anti-fake status: PASS (hard policy for this vertical).

Explicitly forbidden in this vertical until future authorized runtime phase:

1. fake provider status.
2. live integration claims.
3. provider_connected=true without evidence.
4. credential storage.
5. live sync.
6. external submissions.
7. simulated health metrics represented as live telemetry.

Mandatory anti-fake controls:

- Every readiness status must include evidence references.
- Every dashboard tile showing connectivity must remain NON_LIVE unless approved runtime proves otherwise.
- Every API response must preserve no_live_call/no_credentials/no_external_submission semantics while in readiness mode.
- Tenant fail-closed and permission fail-closed behavior is required.
