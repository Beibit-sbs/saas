## 4. Option A - STRICT TENANT ISOLATION
Rules:
- token tenant must equal request tenant on all authenticated endpoints.
- mismatch is always denied (403), regardless of role.
- single future exception path: a future explicit tenant-switch feature (separate session/token issuance), not header override.

Pros:
- strongest isolation guarantee.
- simplest mental model and easiest audit narrative.
- regulatory compliance (Republic of Kazakhstan data residency / ministry oversight) favored.
- lowest cross-tenant data leakage risk.
- matches current runtime behavior end-to-end (no operational change needed to achieve PASS).

Cons:
- reduced direct platform-operations convenience for cross-tenant reads.
- platform operators must use per-tenant sessions or out-of-band tooling.

## 5. Option B - CONTROLLED PLATFORM OVERRIDE
Rules:
- `superadmin` may READ cross-tenant when all of:
  - request method is read-only (`GET`/`HEAD`/`OPTIONS`),
  - explicit token permission `platform.cross_tenant.read`,
  - request audited with `security.cross_tenant.override.allowed`,
  - effective tenant exposed in `request.state` and `tenant_context`,
  - allow-listed routes only.
- non-platform users denied always; writes denied always.

Pros:
- enables future managed-SaaS operational flows (cross-tenant support, oversight dashboards).
- preserves audit + effective tenant visibility through a single decision path.

Cons:
- higher risk surface (one mis-configured permission grant becomes a cross-tenant read).
- larger audit surface to monitor.
- more operational discipline required (permission lifecycle, allow-list curation, audit review).
- divergence between test-runtime PASS and live-runtime FAIL observed in B1 indicates real environments may suppress allow path silently.

## 6. Decision
**Selected policy: Option A - STRICT TENANT ISOLATION.**

Source-of-truth marker:
- `superadmin_cross_tenant_enabled = FALSE`
- `tenant_isolation_policy = STRICT`
- `superadmin_cross_tenant_future_capability = RESERVED`

Decision criteria mapping:
- security: Option A wins (smallest surface).
- university governance: Option A wins (per-tenant institutional autonomy aligns with university operational model).
- auditability: Option A wins (single deny narrative + simple log model).
- future SaaS readiness: Option B preferred *only* if and when managed cross-tenant support is contracted; deferred.
- maintenance cost: Option A wins (no permission lifecycle, no allow-list curation).

Net verdict: Option A is the authoritative tenant governance policy for the current product phase.

Future capability:
- A-044.TENANT-R1's controlled override code stays in the workspace as a *dormant, gated capability*. It is documented but treated as disabled by policy. Reactivation requires:
  - explicit governance decision,
  - allow-list of routes,
  - audited permission grant lifecycle,
  - dedicated baseline action (A-044.TENANT-R2 if ever opened).
