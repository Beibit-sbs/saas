## 6. A-028.1 Expansion L4 Read-Only Visibility Standard

Allowed L4 surfaces:
- tenant-scoped read-only service summaries over existing L3 classifier outputs
- read-only admin API wrappers over those summaries where existing backend permission and tenant patterns already support them
- evidence-backed counts by readiness state and risk band
- evidence-backed missing-evidence aggregation and human review queue counts
- source traceability to existing L3 deterministic contracts

Forbidden L4 surfaces:
- mutations, writes, approvals, submissions, dispatch, closure, deletion, disposal, publication, certification, or enforcement
- provider calls or external side effects
- Brain execution, autonomy, recommendations that self-execute, or workflow execution
- synthetic KPI values, fake dashboards, fake completion flags, fake filing or compliance claims
- cross-tenant reads or implicit tenant inference

Common output fields required for every candidate:
- `tenant_id`
- `module`
- `uce_id`
- `visibility_level` = `L4`
- `source_l3_function`
- `readiness_status_counts`
- `risk_band_counts`
- `human_review_required`
- `human_review_queue_count`
- `missing_evidence_summary`
- `source_evidence_keys`
- `tenant_scoped` = true
- `read_only` = true
- `mutation_performed` = false

Human-review queue meaning:
- queue counts are derived summary counts of records or evidence sets that still require human review under the existing L3 contract
- queue counts do not imply a persisted workflow queue, dispatch capability, or approval action

Permission and RBAC policy:
- service-only surfaces remain internal and tenant-scoped
- API wrappers should use existing admin read boundaries, defaulting to `admin.dashboard.read` unless a stricter pre-existing read permission is already available at runtime integration time
- invalid or missing tenant context must fail closed
- route exposure is limited to admin/read personas and must not imply frontend delivery in A-028.1-RUNTIME
