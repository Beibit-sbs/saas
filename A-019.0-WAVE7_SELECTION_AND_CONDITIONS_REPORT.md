## 7. Selected A-019 Top 5

### 1) Visitor + Access Legacy Contract Stabilization (A-019.1)
- Why selected: closes KC-NEW at source and de-risks all following visitor/access work.
- Current maturity: visitor/access operational but with stale legacy contract tests.
- Missing pieces: contract adapter/alignment in test harness assumptions, payload/version normalization strategy, deterministic assertions.
- Modules: `visitor_management`, `access_control`, test suites around xliii/xlii paths.
- Existing reuse: current routers/services/FSM/event contracts from A-018.
- Brain Core role: stabilizes inbound signal trust for `campus_security` and `visitor_management_ops` decisions.
- KPI/dashboard role: ensures visitor/access event counters stay contract-consistent.
- Risks: accidental regression in existing A-018 behavior if done as broad rewrite.
- Expected step: targeted, additive stabilization + regression contract tests.

### 2) Visitor Management Maturity Completion (A-019.2)
- Why selected: direct continuation from A-018.6 with high operational value.
- Current maturity: Level 4 operational.
- Missing pieces: deeper frontend workflow UX, stronger host-review evidence surfaces, tighter lifecycle validation contracts.
- Modules: `visitor_management`, frontend visitor page/hooks, dashboard integration.
- Existing reuse: 7-state FSM, router endpoints, event ingestion mapping, KPI keys.
- Brain Core role: enrich `visitor_management_ops` evidence and recommended actions.
- KPI/dashboard role: stronger visitor throughput + exception slices.
- Risks: UI/data contract drift.
- Expected step: lifecycle completion and contract hardening.

### 3) Security Operations Incident Brain (A-019.3)
- Why selected: high security and rector/admin value, ready for deeper reasoning.
- Current maturity: Level 4 operational.
- Missing pieces: richer escalation policy states, explicit human-approval checkpoints, incident context enrichment.
- Modules: `security_operations`, `brain_core`, `audit`, notifications.
- Existing reuse: incident events, `campus_security` scenario, existing security pages/tests.
- Brain Core role: primary decision/scenario expansion.
- KPI/dashboard role: incident severity/escalation visibility.
- Risks: scope creep into automation beyond policy limits.
- Expected step: additive incident-brain policy expansion with review gates.

### 4) Visitor Access Workflow Integration (A-019.4)
- Why selected: highest cross-module integration payoff after stabilization.
- Current maturity: partially proven by A-018.7 E2E.
- Missing pieces: explicit end-to-end workflow contracts from visitor approval -> access decisions -> security response.
- Modules: `visitor_management`, `access_control`, `security_operations`, `audit`, event/kpi pipeline.
- Existing reuse: A-018.7 cross-feature patterns and event lineage.
- Brain Core role: unifies risk context across visitor/access/security.
- KPI/dashboard role: joined workflow counters and anomaly trends.
- Risks: brittle integration tests if contracts are underspecified.
- Expected step: targeted integration contracts + deterministic E2E slices.

### 5) Security Operations KPI / Dashboard (A-019.5)
- Why selected: converts backend capability into executive operational evidence.
- Current maturity: baseline campus ops KPI exists.
- Missing pieces: deeper security panel composition and explicit non-destructive policy indicators.
- Modules: `platform/kpi`, `dashboard`, `security_operations`, `visitor_management`.
- Existing reuse: Wave 6 metric lineage and dashboard patterns.
- Brain Core role: exposes reasoning outcomes and recommended human actions.
- KPI/dashboard role: core deliverable.
- Risks: metric inflation/duplication if lineage rules are not tightened.
- Expected step: KPI contract consolidation + dashboard section hardening.
