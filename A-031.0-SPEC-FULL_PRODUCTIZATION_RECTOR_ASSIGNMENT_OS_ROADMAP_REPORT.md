## 5. Selected Product Vertical

### Rector Assignment / Execution Control OS

**Primary users**: Rector, Vice Rector / Prorectors, Directors/Deans, Executors, Controllers/Secretary, Auditors/Observers, Platform Admin

**Core value proposition**:
> A university leader (rector or prorector) creates an assignment — strategic, regulatory, or operational. The assignment is routed to an accountable unit (department, dean, director). The executor accepts and executes. At defined intervals (weekly or ad hoc), the executor submits a report with progress, blockers, and evidence. The controller reviews and either approves or returns for revision. Overdue assignments trigger escalation. Leadership sees a live executive dashboard. Every action is audited.

**Product boundaries**:
- Real data-backed workflows (no fake/hardcoded metrics)
- Tenant-isolated (no cross-tenant access)
- RBAC/ABAC enforced (no role escalation)
- Audit trail for every mutation
- No autonomous AI completion — human review required for all transitions
- No direct external submission in first runtime
- No hard delete for official records

## 10. Assignment Lifecycle

### Status Definitions

| Status | Description |
|--------|-------------|
| DRAFT | Created but not yet published; only visible to creator |
| ASSIGNED | Published and routed to assignee unit/person |
| ACCEPTED | Executor has acknowledged and accepted the assignment |
| IN_PROGRESS | Active execution underway |
| REPORT_SUBMITTED | Executor submitted a progress report; awaiting review |
| RETURNED_FOR_REVISION | Reviewer returned report; executor must revise |
| COMPLETED | Reviewer confirmed assignment is done; officially closed |
| OVERDUE | Past due_date without being COMPLETED; computed, not manually set |
| ESCALATED | Triggered by overdue policy or manual escalation |
| CANCELLED | Officially cancelled (with reason and audit); not hard deleted |
| ARCHIVED | Long-term storage state; read-only |

### Transition Rules

```
DRAFT        → ASSIGNED                (creator publishes; requires assignee)
ASSIGNED     → ACCEPTED                (executor acknowledges)
ASSIGNED     → CANCELLED               (creator cancels before acceptance)
ACCEPTED     → IN_PROGRESS             (executor begins work)
IN_PROGRESS  → REPORT_SUBMITTED        (executor submits report)
REPORT_SUBMITTED → IN_PROGRESS         (reviewer returns for revision)
REPORT_SUBMITTED → RETURNED_FOR_REVISION (reviewer requests changes)
RETURNED_FOR_REVISION → REPORT_SUBMITTED (executor resubmits)
REPORT_SUBMITTED → COMPLETED           (reviewer approves; assignment complete)
IN_PROGRESS  → OVERDUE                 (computed by scheduler when past due_date)
ACCEPTED     → OVERDUE                 (computed by scheduler when past due_date)
OVERDUE      → ESCALATED               (policy-triggered or manual)
OVERDUE      → COMPLETED               (reviewer completes despite late)
ESCALATED    → IN_PROGRESS             (escalation resolved; work continues)
ESCALATED    → COMPLETED               (escalation resolved with completion)
any          → CANCELLED               (authorized actor with reason; audit required)
COMPLETED    → ARCHIVED                (after retention period)
CANCELLED    → ARCHIVED                (after retention period)
```

### Invariants
- OVERDUE is computed from `due_date` — never manually set
- Every transition creates an `AssignmentStatusHistory` record and an `AssignmentAuditEvent`
- Tenant isolation is enforced on every read and write
- No transition bypasses RBAC check
- COMPLETED and ARCHIVED states are immutable (no reverse transition)

## 11. Core Workflows

### Workflow 1 — Create Assignment

| Attribute | Detail |
|-----------|--------|
| Actor | RECTOR, VICE_RECTOR, CONTROLLER (with permission), PLATFORM_ADMIN |
| Input | title, description, priority, due_date, category, optional recurrence, optional template |
| Validation | tenant_id valid; actor has can_create_assignment; title non-empty; due_date in future; priority valid |
| State transition | None → DRAFT |
| Audit event | CREATED |
| Notification | None at DRAFT (optional configurable) |
| Permission | can_create_assignment |
| Failure modes | tenant mismatch → 403; missing required fields → 422; past due_date → 422 |

### Workflow 2 — Assign to Unit/Person

| Attribute | Detail |
|-----------|--------|
| Actor | RECTOR, VICE_RECTOR, CONTROLLER (with permission) |
| Input | assignment_id, assignee_unit (required), assignee_user_id (optional), task definitions |
| Validation | assignment in DRAFT; actor has can_assign_executor; assignee_unit valid within tenant |
| State transition | DRAFT → ASSIGNED |
| Audit event | ASSIGNED |
| Notification | Outbox: notify assignee (executor/director) of new assignment |
| Permission | can_assign_executor |
| Failure modes | assignment not in DRAFT → 409; executor not in tenant → 403 |

### Workflow 3 — Accept Assignment

| Attribute | Detail |
|-----------|--------|
| Actor | EXECUTOR (or DIRECTOR for unit-level acceptance) |
| Input | assignment_id, optional acceptance note |
| Validation | assignment in ASSIGNED; actor is designated assignee; tenant match |
| State transition | ASSIGNED → ACCEPTED |
| Audit event | ACCEPTED |
| Notification | Outbox: notify originator of acceptance |
| Permission | can_view_department_assignments (implied accept right for assignee) |
| Failure modes | assignment not in ASSIGNED → 409; actor not assignee → 403 |

### Workflow 4 — Submit Weekly/Periodic Report

| Attribute | Detail |
|-----------|--------|
| Actor | EXECUTOR |
| Input | assignment_id, reporting_period, progress_percent (0–100), summary (required), blockers (optional), next_steps (optional) |
| Validation | assignment in IN_PROGRESS or ACCEPTED or OVERDUE or RETURNED_FOR_REVISION; actor is assignee; progress_percent 0–100 integer; summary non-empty |
| State transition | IN_PROGRESS / ACCEPTED / OVERDUE / RETURNED_FOR_REVISION → REPORT_SUBMITTED |
| Audit event | REPORT_SUBMITTED |
| Notification | Outbox: notify controller/originator of report submission |
| Permission | can_submit_report |
| Failure modes | invalid state → 409; progress out of range → 422; summary empty → 422 |

### Workflow 5 — Attach Evidence

| Attribute | Detail |
|-----------|--------|
| Actor | EXECUTOR, DIRECTOR, VICE_RECTOR, RECTOR, CONTROLLER |
| Input | assignment_id, optional report_id, evidence_type, file/link, title |
| Validation | assignment exists in tenant; actor has can_attach_evidence; file size ≤ limit; link URL sanitized |
| State transition | None (evidence is supplementary; does not change assignment status) |
| Audit event | EVIDENCE_ATTACHED |
| Notification | None (optional configurable) |
| Permission | can_attach_evidence |
| Failure modes | file too large → 413; link not sanitized → 422; assignment not found → 404 |

### Workflow 6 — Review / Return / Complete

| Attribute | Detail |
|-----------|--------|
| Actor | RECTOR, VICE_RECTOR, CONTROLLER |
| Input (return) | assignment_id, report_id, review_comment (required for return) |
| Input (complete) | assignment_id, optional final_note |
| Validation | assignment in REPORT_SUBMITTED; actor has can_return_for_revision or can_mark_completed |
| State transition (return) | REPORT_SUBMITTED → RETURNED_FOR_REVISION |
| State transition (complete) | REPORT_SUBMITTED → COMPLETED |
| Audit event | REPORT_RETURNED / REPORT_APPROVED / STATUS_CHANGED (COMPLETED) |
| Notification | Outbox: notify executor of review decision |
| Permission | can_return_for_revision, can_mark_completed |
| Failure modes | assignment not in REPORT_SUBMITTED → 409; review_comment empty on return → 422 |

### Workflow 7 — Overdue Escalation and Dashboard Visibility

| Attribute | Detail |
|-----------|--------|
| Actor | Scheduler (system) or RECTOR/CONTROLLER (manual) |
| Input | assignment_id (manual) or scheduled policy config |
| Validation | assignment is OVERDUE or past due_date; policy defines escalation_level; actor has can_escalate |
| State transition | OVERDUE → ESCALATED |
| Audit event | OVERDUE_DETECTED, ESCALATED |
| Notification | Outbox: notify escalated_to_role (director, vice_rector, rector as appropriate) |
| Dashboard update | AssignmentDashboardSummary.overdue_count and escalated_count reflect real computed values |
| Permission | can_escalate |
| Failure modes | assignment not OVERDUE → 409 (for manual trigger); policy not configured → skip with log |
| Anti-fake note | overdue_count in dashboard MUST be computed from real due_date comparison — never hardcoded |

## 15. Security / Tenant / Audit Requirements

### Security

| Requirement | Detail |
|------------|--------|
| No SQL injection | All queries use parameterized statements / ORM; never raw string interpolation |
| No IDOR | Every resource read verifies `resource.tenant_id == request.tenant_id` |
| No privilege escalation | Role not writable by user; managed by PLATFORM_ADMIN only |
| CSRF protection | Cookie auth + SameSite + CSRF token on mutating endpoints |
| Evidence file validation | MIME type checked; size limit enforced; no server-side code execution from uploads |
| Link sanitization | All link_url fields validated against allowlist scheme (https only); no javascript: |
| Audit immutability | AssignmentAuditEvent is insert-only; no UPDATE/DELETE on audit table |
| No secret in logs | user passwords, tokens, file storage credentials never logged |

### Tenant Isolation

- tenant_id extracted from authenticated session only — never from request body for security-critical lookups
- All FK joins include tenant_id filter
- Cross-tenant assignment reference is forbidden
- Tenant-level SLA policy is isolated

### Audit

- Every state transition → AssignmentStatusHistory + AssignmentAuditEvent
- Every evidence attachment → AssignmentAuditEvent(EVIDENCE_ATTACHED)
- Every comment → AssignmentAuditEvent(COMMENT_ADDED)
- Audit events include: actor_user_id, actor_role, request_id, old_value, new_value, occurred_at
- Audit trail API is read-only; no deletion
- Retention: audit events retained per tenant retention policy (configurable; minimum 7 years for official records)

## 17. Notification / Outbox Expectations

### Outbox Pattern

- Notifications are written to an `outbox_notifications` table as part of the same DB transaction as the triggering event
- No direct SMTP, SMS, or webhook calls in request path
- A background worker (separate process or scheduled job) polls outbox and dispatches
- Failed dispatches: retry with exponential backoff; max_retries configurable
- Notification deduplication: idempotency_key per event+recipient combination

### Notification Events (A-031 scope)

| Event | Recipient | Channel (future) |
|-------|-----------|------------------|
| Assignment ASSIGNED | Assignee executor/director | In-app + email |
| Assignment ACCEPTED | Originator | In-app |
| Report SUBMITTED | Controller, originator | In-app + email |
| Report RETURNED | Executor | In-app + email |
| Report APPROVED / COMPLETED | Executor | In-app |
| Assignment OVERDUE | Executor, controller, originator | In-app + email |
| Assignment ESCALATED | Escalated-to role | In-app + email |
| Escalation RESOLVED | Executor, originator | In-app |

### First Runtime Scope
- Outbox table creation and write only
- Dispatch worker is deferred to A-031.5 or later
- Dashboard/UI can show notification log from outbox in read mode
