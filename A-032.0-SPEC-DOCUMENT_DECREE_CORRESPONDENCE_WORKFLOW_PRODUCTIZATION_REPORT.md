## 4. Strategic Product Decision

**Selected next vertical:**

### DOCUMENT / DECREE / CORRESPONDENCE WORKFLOW OS

**Product code**: `DOCUMENT_DECREE_CORRESPONDENCE_WORKFLOW_OS`

**Rationale:**

The Rector Assignment OS established the lifecycle of work assignment and execution tracking inside the rectorate. The natural governance continuation is:

```
Rector Assignment OS
  └─► Resolution / Decree
        └─► Official Document
              └─► Incoming / Outgoing Correspondence
                    └─► Execution Control (links back to assignments)
                          └─► Report / Evidence
                                └─► Audit → Archive
```

This creates a closed-loop governance system:

1. Assignments generate action items
2. Completed actions generate resolutions/decrees
3. Decrees become registered official documents
4. Documents trigger correspondence workflows
5. Correspondence routes to departments
6. Departments execute via assignments
7. Evidence closes the loop
8. Archive preserves the institutional record

**Why now:**
- Six L2 foundation modules already exist (implemented in A-027.x)
- These modules have lifecycle status definitions, tenant validation, forbidden actions defined
- They are L2 FOUNDATION_READY but lack: models, DB, routes, frontend, tests
- Productization lifts them to L3→L4→L5

## 7. Product Users and Roles

### Role Definitions

**Role 1: Rector / Executive Sponsor** (`rector`)
- Responsibilities: Issue resolutions and decrees; review critical documents; authorize signed orders
- Allowed actions: Sign resolutions (human-only), view dashboard, assign follow-up, review pending decrees, approve final documents
- Forbidden actions: Auto-impersonation, auto-approval by system, auto-signing, mass delete
- Route/page visibility: All `/console/documents/` routes; dashboard; decree signing workflow
- Audit expectations: All sign/approve actions fully audit-logged with user ID + timestamp

**Role 2: Vice Rector / Prorector** (`prorector`)
- Responsibilities: Review documents before rector; pre-approve decrees; oversight
- Allowed actions: Review documents, return for revision, pre-approve, route for rector attention
- Forbidden actions: Final signing on behalf of rector, mass archive without approval
- Audit expectations: All review/pre-approve audit-logged

**Role 3: Chancellery / Office Clerk** (`chancellery_clerk`)
- Responsibilities: Register incoming/outgoing correspondence; assign registry numbers; route documents
- Allowed actions: Create/register correspondence, assign registry number, route to department, create document drafts
- Forbidden actions: Approve on behalf of rector, alter registry number after registration, delete records
- Route/page visibility: `/console/documents/correspondence`, document registry list
- Audit expectations: Registry number assignment audit-logged; routing audit-logged

**Role 4: Document Controller** (`document_controller`)
- Responsibilities: Manage document lifecycle; track document status; coordinate review
- Allowed actions: Create documents, update drafts, submit for review, track status, archive completed
- Forbidden actions: Approve/sign, assign registry numbers (chancellery only), hard delete
- Audit expectations: All mutations audit-logged

**Role 5: Department Director / Dean** (`department_director`)
- Responsibilities: Review documents relevant to department; respond to incoming correspondence routed to department; coordinate executor
- Allowed actions: Review and comment, request revision, route to executor, submit department response
- Forbidden actions: Issue decrees, assign registry numbers
- Audit expectations: All review actions logged

**Role 6: Executor** (`document_executor`)
- Responsibilities: Execute document-linked assignments; submit evidence/reports
- Allowed actions: View assigned documents, submit execution report, upload evidence attachments
- Forbidden actions: Alter official registry metadata, approve/sign, modify document title/type after registration
- Audit expectations: All evidence submissions logged

**Role 7: Legal / Compliance Reviewer** (`legal_reviewer`)
- Responsibilities: Review decrees for legal compliance; flag issues
- Allowed actions: Read decree, add legal review note, flag for revision, approve legal compliance (not final approval)
- Forbidden actions: Issue decrees, auto-approve legal status, modify document body
- Audit expectations: All legal review actions logged

**Role 8: Auditor / Observer** (`document_auditor`)
- Responsibilities: Read-only access to all documents, decrees, correspondence, audit trails
- Allowed actions: Read all records, read audit trail, export summary
- Forbidden actions: Any mutation (create, update, archive, approve, sign)
- Route/page visibility: All read-only; `/console/documents/*/audit`
- Audit expectations: Access log (read access on sensitive records)

**Role 9: Platform Admin** (`platform_admin`)
- Responsibilities: Platform-level configuration; user/role management; system health
- Allowed actions: All admin actions including tenant configuration, role assignment, archive management
- Forbidden actions: Bypass audit trail, auto-sign on behalf of rector
- Audit expectations: All admin mutations audit-logged

## 8. Document Workflow Lifecycle

### Document Statuses

```
DRAFT
  │
  ▼
REGISTERED ────────────────── registry_number assigned
  │
  ▼
UNDER_REVIEW ─────────────── reviewer assigned
  │        │
  ▼        ▼
RETURNED_  APPROVED ───────── all reviewers pass
FOR_REVISION
  │           │
  ▼           ▼
DRAFT       SIGNED ─────────── rector signature (human-only)
              │
              ▼
            ISSUED ─────────── official issue
              │
              ├──► SENT (if outgoing)
              │
              ├──► RECEIVED (if incoming acknowledgment)
              │
              ▼
            LINKED_TO_ASSIGNMENT ── linked to executor assignment
              │
              ▼
            IN_EXECUTION
              │
              ▼
            EXECUTION_REPORTED ── evidence submitted
              │
              ▼
            ARCHIVED ────────── soft archive (no hard delete)
              │
(at any stage)
              ▼
            CANCELLED ────────── explicit cancellation, audit-logged
```

### Transition Rules
1. Registry number assigned only at `REGISTERED` state; immutable thereafter (except correction workflow)
2. Transition `APPROVED → SIGNED` requires explicit human action; no auto-signing
3. `ARCHIVED` and `CANCELLED` are terminal states; no hard delete
4. Every transition audit-logged with: user_id, from_status, to_status, timestamp, optional_note
5. No backward transitions except `RETURNED_FOR_REVISION → DRAFT → REGISTERED` re-submission path
6. `LINKED_TO_ASSIGNMENT` can coexist with IN_EXECUTION (sub-state)

## 9. Order / Decree Lifecycle

### Decree/Order Statuses

```
DRAFT_ORDER
  │
  ▼
LEGAL_REVIEW ─────────────── legal reviewer assigned
  │        │
  ▼        ▼
RETURNED_  LEGAL_APPROVED (compliance only, not final)
FOR_REVISION
  │              │
  ▼              ▼
DRAFT_ORDER   RECTOR_REVIEW ── rector reviews (human)
                │
                ▼
             APPROVED_FOR_SIGNING ── all pre-approvals complete
                │
                ▼
             SIGNED ─────────── rector signature (human-only action)
                │
                ▼
             REGISTERED ───────── registry number assigned
                │
                ▼
             PUBLISHED_INTERNAL ── available to authorized roles
                │
                ▼
             ASSIGNED_FOR_EXECUTION ── generates linked assignments
                │
                ▼
             EXECUTION_TRACKED ── tracking active
                │
                ▼
             COMPLETED ────────── execution evidence received
                │
                ▼
             ARCHIVED ─────────── soft archive
(at any stage)
                ▼
             CANCELLED ────────── explicit, audit-logged
```

### Decree Rules
1. No auto-signing under any circumstances
2. No auto-approval by system — every approval is a human action recorded with user_id
3. No auto-legal-decision — legal review is advisory, not autonomous
4. Registry number never auto-generated without explicit registration step
5. No backdated registry number unless marked with `is_correction=True` + reason + approver_id
6. `ASSIGNED_FOR_EXECUTION` transitions generate linked assignments only after human confirmation
7. All changes audit-logged; no silent mutations

## 10. Correspondence Lifecycle

### Incoming Correspondence

```
RECEIVED ─────────────────── letter/document arrives
  │
  ▼
REGISTERED ───────────────── registry number assigned by chancellery
  │
  ▼
CLASSIFIED ───────────────── correspondence type/priority set
  │
  ▼
ROUTED ────────────────────── assigned to department/executor
  │
  ▼
ASSIGNED ──────────────────── executor receives task
  │
  ▼
IN_PROGRESS ───────────────── response being prepared
  │
  ▼
RESPONDED ─────────────────── response sent/recorded
  │
  ▼
ARCHIVED ──────────────────── soft archive
```

### Outgoing Correspondence

```
DRAFT ─────────────────────── initial draft
  │
  ▼
UNDER_REVIEW ──────────────── reviewer assigned
  │        │
  ▼        ▼
RETURNED   APPROVED ──────── approval recorded
FOR_DRAFT
            │
            ▼
          REGISTERED ──────── outgoing registry number assigned
            │
            ▼
          SENT ──────────────── dispatch event recorded (metadata only)
            │
            ▼
          DELIVERED_METADATA_ONLY ─ metadata confirmation only
            │
            ▼
          ARCHIVED ────────── soft archive
```

### Correspondence Rules
1. Delivery status is **metadata only** — no live provider dispatch in A-032 initial runtime
2. No automatic `SENT`/`DELIVERED` claim without explicit human confirmation
3. No external email/SMS/postal system integration in initial runtime
4. No fake sent/delivered claim
5. `DELIVERED_METADATA_ONLY` explicitly communicates that delivery confirmation is metadata, not provider-confirmed
6. Registry number for incoming vs outgoing use separate sequences (INB-YYYY-NNNN vs OUT-YYYY-NNNN)
7. All routing actions audit-logged

## 14. Rector Assignment OS Integration

### Integration Points

**1. Document → Rector Assignment**
- A document in `ISSUED` or `LINKED_TO_ASSIGNMENT` state can create a linked rector assignment
- The assignment references `source_document_id` and `linked_document_id`
- Assignment creation requires explicit human action (no automatic assignment generation)
- Status updates flow independently: document status and assignment status are not auto-synced

**2. Decree → Rector Assignment**
- A signed and registered decree can generate an execution assignment
- The `OrderDecree.linked_assignment_id` field holds the reference
- Transition from `PUBLISHED_INTERNAL` to `ASSIGNED_FOR_EXECUTION` requires human confirmation
- The generated assignment is a standard rector assignment with the decree as source

**3. Incoming Correspondence → Rector Assignment**
- A routed incoming correspondence item can be converted to a rector assignment by a document controller or prorector
- `CorrespondenceItem.linked_assignment_id` tracks this link
- No automatic assignment creation from correspondence; always human-initiated

**4. Rector Assignment Reports → Document Archive**
- Assignment evidence/reports can be linked back to a parent document via `DocumentAssignmentLink`
- Assignment completion evidence can be attached as a `DocumentVersion` or `DocumentAuditEvent`
- No reverse mutation: assignment completion does not automatically close/archive a document

### Integration Rules
1. No circular mutation: document state changes do not auto-trigger assignment state changes
2. No automatic assignment creation from any document/decree/correspondence transition
3. All links are explicit human actions recorded with user_id
4. Audit logged on both sides (document audit and assignment audit)
5. No fake link status (e.g., no auto-COMPLETED assignment from document approval)

## 17. Audit / Security / Tenant Requirements

### Tenant Isolation (Mandatory)
- `tenant_id` column on every entity
- `tenant_id` filter on every query — no cross-tenant data access
- No global list endpoints without tenant scope
- Tenant ID sourced from JWT auth context, not from request body

### Audit Requirements (Mandatory)
- `DocumentAuditEvent` row created for every mutation
- Status transition recorded in `DocumentStatusHistory`
- Audit events include: event_type, performed_by_user_id, performed_at, detail (JSON)
- Audit trail is read-only (no mutation of audit records)
- Audit trail queryable by document/decree/correspondence ID

### Archive / Deletion Policy
- **No hard delete** anywhere in the system
- Archive = soft state change (entity moves to `ARCHIVED` status + `archived_at` timestamp)
- Archive action itself is audit-logged
- `ArchiveRecord` entity tracks all archived items for admin reference
- No `DROP TABLE`, no `DELETE FROM` with cascade, no bulk hard delete

### Registry Number Integrity
- Registry numbers assigned only at explicit registration step (human action)
- Registry number immutable after assignment
- Exception: correction workflow requires `is_correction=True`, `correction_reason`, and approver_id
- No auto-generated registry numbers without registration event

### Security Rules
- RBAC via permission_dependency on every route
- No route accessible without authentication
- No service-level bypass of tenant filter
- No direct DB access from frontend (all via API)
- No document content stored in initial runtime (metadata only — full content management deferred)
- No PII in audit event detail fields beyond user_id references
- Input validation on all create/update endpoints

## 18. Anti-Fake Boundaries

The following are explicitly forbidden in A-032 initial runtime implementation:

| Forbidden Action | Reason |
|---|---|
| Auto-signing of decrees/documents | Signing is a human legal act |
| Auto-approval by system | Approval requires human review |
| Auto-legal-decision | Legal review is advisory, not autonomous |
| Fake registry number | Registry numbers are official record identifiers |
| Backdated registry number (without correction flag) | Official records cannot be altered without audit |
| Fake `SENT`/`DELIVERED` status | Delivery requires live provider confirmation |
| Provider integration (email/SMS/postal) | No external dispatch in A-032 initial runtime |
| AI-generated official document body | No AI authoring of official records |
| AI-generated approval decision | No autonomous legal/compliance decisions |
| Fake dashboard metrics | All KPIs must be computed from real DB queries |
| Hidden deletion of records | Archive-only; no hard delete |
| Silent mutation of official records | All changes audit-logged |
| L5/L6 maturity claim | Current metrics stay at L3/L4 ceiling |
| Production-ready claim | Controlled institutional rollout sequence applies |
| Cross-tenant data access | Tenant isolation is hard requirement |
| Auto-execution of assignments from decrees | Requires explicit human confirmation |
| OCR/AI document content analysis | Deferred to future capability addition |
