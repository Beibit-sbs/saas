# A-055.HSP-R1 Hardening - Hardship Chain Review Remediation Report

## Scope

Remediate confirmed findings from the adversarial review of the
student_services_support hardship write chain (A-055.20-.27). The review produced
16 findings, each independently verified. **9 confirmed, 7 refuted.** The 7
refutals confirmed the chain's SECURITY posture is sound (source_flow precondition
enforced, RBAC correct, tenant scoping correct, anti-fake/no-money-movement intact)
— the real defect is workflow/transition integrity.

## Core fix — the human-review gate was not enforced

**Confirmed (findings 1, 3, 8, 9):** hardship status transitions were applied
BLINDLY with no allowed-map and no terminal-state guard. `_validate_transition`
existed but was wired only to service-request status; there was NO hardship
transition map. Consequences (all reproducible by an already-write-authorized
caller acting out of order, within the metadata-only/no-money flow):
- a finance-office referral could be recorded DIRECTLY on a freshly-created
  `readiness_evaluated` hardship — **skipping the human-review-outcome gate** — and
  the bypassed referral appeared in the referral queue indistinguishably from a
  properly-reviewed one (audit-integrity hole);
- the contract-terminal `finance_office_referral_recorded` state could be silently
  re-mutated / appended;
- evidence-gap intake could run after a referral, flipping readiness back while
  status stayed terminal (inconsistent record).

**Fix:** added `_HARDSHIP_ALLOWED_TRANSITIONS`
(`readiness_evaluated -> human_review_outcome_recorded -> finance_office_referral_recorded`,
terminal) + `_validate_hardship_transition`, and applied it:
- human-review-outcome-note: require the transition from the current status;
- finance-office-referral: require `human_review_outcome_recorded` first (enforces the gate);
- evidence-gap intake: rejected once terminal (`finance_office_referral_recorded`).
Invalid order -> `DomainValidationError` -> router maps to 400; nothing is persisted.

## Tests

Added 3 rejection tests (out-of-order -> 400, nothing persisted): referral
skipping human-review; outcome-note on a terminal hardship; evidence-gap after
referral. The existing in-order tests already used the correct prior statuses and
continue to pass (they were the positive-path coverage).

## Confirmed but deferred (documented, not silently dropped)

- **F2/F6 (test infra):** the queue/dashboard round-trip uses a Postgres-only JSONB
  `metadata_json['source_flow']` filter, exercised only by mock-based unit tests; a
  real-Postgres integration test would pin it end-to-end. Deferred (needs a real DB
  in the harness).
- **F4/F5 (HTTP-level tests):** positive coverage exists at the service level (the
  in-order tests + the new rejection tests); TestClient HTTP-level success/denial
  tests for each hardship endpoint are a follow-up.
- **F7 (queue accounting):** the reviewer queue / `review_queue_count` do not exclude
  terminal statuses, so a referred hardship still shows in the reviewer queue.
  Refinement deferred (filter terminal statuses out of the reviewer view).

## Lesson (reinforced)

Same theme as the finance acknowledge bug: the test suite only proved structure /
in-order happy paths, so an out-of-order gate-bypass shipped invisibly. Workflow
state machines need explicit transition validation AND negative (out-of-order)
tests, not just happy-path coverage.
