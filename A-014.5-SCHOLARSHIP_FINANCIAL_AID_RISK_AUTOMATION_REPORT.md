## Scope

Wire scholarship award at-risk events (`scholarship.award.at_risk_detected`) and financial-aid warning events (`financial_aid.warning.detected`) into the existing Brain Core `student_support_bridge` scenario, so that:

1. Scholarship and financial-aid risk signals produce support cases and advisor notifications.
2. High-severity signals route to `approval_pending` (gated dispatch); medium-severity signals are dispatched immediately.
3. Signals missing `student_id` are fail-closed (rejected with reason `missing_student_context`).
4. Duplicate signals are deduplicated per-tenant.
5. Action payloads carry domain-specific reference fields (`award_id`, `application_id`, `record_id`).

All changes are strictly additive (no new tables, migrations, or public endpoints).

## Architecture Notes

### Signal Path: Scholarship Award At-Risk

```
scholarship.award.at_risk_detected
  → _normalize_scholarship_award_risk_signal()  ← FAIL-CLOSED if no student_id
  → registry: student_support_bridge scenario
  → risk_classifier: scholarship_award_risk_high | scholarship_award_risk_medium
  → rules_engine: risk/critical → approval_pending | preventive/medium → dispatched
  → planner: build_plan() with award_id in action payload
  → policy_guard: approval_pending gates dispatch_results
  → student_support actions: create_student_support_case, notify_student_success_team, notify_advisor
```

### Signal Path: Financial Aid Warning

```
financial_aid.warning.detected
  → existing normalization (no fail-closed needed, student_id always present)
  → registry: student_support_bridge scenario
  → risk_classifier: financial_aid_warning_high → risk/critical
  → rules_engine: risk/critical → approval_pending
  → planner: build_plan() with record_id, application_id in action payload
  → policy_guard: approval_pending; caller must invoke approve_decision() to dispatch
```

### Approval Flow for High-Severity Actions

`risk/critical` decisions have `status == "approval_pending"` and `dispatch_results == []` until
`service.approve_decision(decision_id)` is called. This is by design — high-severity scholarship
and financial-aid interventions require human approval before actions are dispatched.

### Fail-Closed Pattern

`_normalize_scholarship_award_risk_signal()` mirrors the existing `_normalize_degree_progress_signal()` pattern:
- Extracts `student_id` from payload / subject / top-level
- Returns `(normalized_signal, "missing_student_context")` if absent
- `process_signal()` returns `{"status": "rejected", "reason": "missing_student_context"}` without further processing

### Planner Payload Extension

`ActionPlanner.build_plan()` now extracts and propagates `award_id`, `application_id`, `record_id` in every
action item's payload dict. These are `None`-safe — events that don't supply them carry `None` values,
which is backwards-compatible with all existing action handlers.
