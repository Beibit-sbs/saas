### Models Pattern
Each domain model includes:
- `id` (UUID primary key)
- `tenant_id` / `org_id` (multi-tenant scoping)
- `created_at` (ISO8601 timestamp)
- `updated_at` (ISO8601 timestamp, immutable for audit tables)
- Domain-specific fields (per contract)
- `source_context` (audit trail: which service created record)

### Schemas Pattern
Each domain includes:
- Request schema (read-only queries only in A-054.4)
- Response schema (include all fields required by API contract)
- Filter schema (for query parameters)
- Pagination schema (limit, offset)

### Service Layer Pattern
Each service implements:
- `get_by_id()` — fetch single record
- `query()` — filtered, paginated queries
- `apply_tenant_filter()` — enforce org/recipient scoping
- `apply_rbac_filter()` — enforce permission-based visibility
- For audit tables: `append()` (immutable insert only)
- For provider: `get_readiness_status()` (status-only, no connection)

## Brain Signal / Action Implementation Plan

### Brain Communication Action Proposal Lifecycle

**Phase 1: Signal Ingestion (Brain Core → Communications)**
- Brain Core sends communication signal proposal to communications module
- Signal types: academic_risk, low_attendance, course_failure, exam_violation, late_fee, etc.
- Proposal includes: source_signal_id, urgency_level, target_group_id, recommended_template_id

**Phase 2: Policy Validation**
- Communications module validates proposal against policy gates:
  - Template compliance: Template exists, parameters valid, channels available
  - Recipient validation: Group verified, members exist, preferences honored
  - Escalation policy: If unresolved escalation exists, apply gate
  - Emergency policy: If critical level, require rector approval
  - Bulk policy: If >100 recipients, require approval

**Phase 3: Approval Workflow**
- Proposal stored in `CommCommunicationAction` with `approval_status=pending`
- Approval chain determined by urgency_level:
  - low: Manager approval (default)
  - medium: Director approval
  - high: Executive approval
  - critical: Rector approval
- Approval routed to designated role

**Phase 4: Execution (Future)**
- Once approved, Communications sends notifications through Notification Center
- Execution logged in `CommCommunicationActionExecution`
- Each notification links back to action proposal

**Phase 5: Outcome Feedback**
- User interactions with notifications recorded (delivered, read, clicked)
- Feedback stored in `CommActionOutcomeFeedback`
- Brain Core polls feedback to refine future signal timing/targeting

### Approval Gates

**Template Compliance Gate:**
- Recommended template must exist
- All required parameters must be mappable from signal
- Template must be active
- Channels (email, sms, push) must be available

**Recipient Validation Gate:**
- Target group must be defined and non-empty
- All group members must have valid recipient records
- Recipient preferences checked: quiet hours respected, opt-outs honored
- No arbitrary targeting allowed

**Escalation Gate:**
- If high/critical urgency: Check for existing unresolved escalations
- Escalation must be completed before sending high-priority notifications
- Prevents notification spam during escalation

**Emergency Gate:**
- Critical urgency requires Emergency Broadcast Registry policy
- Rector-level approval mandatory
- Multi-level approval chain enforced
- Test mode available (no actual send)

**Bulk Notification Gate:**
- Recipients >100 requires explicit approval
- ROI review: Estimated engagement vs cost
- Rate limit check: Can system handle volume?
- Approval by communications director or admin

### Policy Validation Points

**Defined in `CommBrainSignalValidator`:**
```python
def validate_template_compliance(proposal) -> bool
def validate_recipient_group(proposal) -> bool
def validate_escalation_status(proposal) -> bool
def validate_emergency_policy(proposal) -> bool
def validate_bulk_limits(proposal) -> bool
```

**Each validator returns:** (is_valid, reason, required_approvals)

### Feedback Loop

**Recorded Feedback Types:**
- `delivered`: Notification successfully sent
- `read`: User opened/read notification
- `clicked`: User clicked link in notification
- `escalated`: User action triggered escalation
- `resolved`: User problem resolved (from action outcome form)
- `bounced`: Delivery failed (from audit trail)

**Feedback Storage:**
- `CommActionOutcomeFeedback` table
- Linked to action proposal and notification
- Timestamp and details recorded
- Brain Core queries feedback via new endpoint (future)

**Brain Core Refinement Use Cases:**
- Template effectiveness: Which templates have highest read rates?
- Timing optimization: When do users engage most?
- Targeting refinement: Which groups respond best to which signals?
- Policy adjustment: Are approval gates too strict/lenient?

### Blocked Autonomous Actions

**Never Autonomous:**
- Emergency broadcasts: Always require rector approval (no auto-activation)
- Critical escalations: Always route to human for decision
- Bulk campaigns >100: Always require director approval
- Parent communication: Always require staff review

**Always Require Approval:**
- communications.emergency.activate (rector only)
- communications.escalations.approve (for high/critical)
- communications.campaigns.execute (for bulk >100)
- communications.moderation.approve (staff review)

**Approval UI Shows:**
- Approval status: pending, approved, denied
- Approval chain: Who needs to approve? Current approver?
- Expected timeline: How long does approval take?
- Reason for approval: Why is this action policy-gated?

### Emergency / Bulk / Parent Communication Gates

**Emergency Broadcast Gate:**
- Activation_criteria must be explicitly met

- Test mode available (marks messages "TEST - NOT SENT")

**Bulk Notification Gate (>100 recipients):**
- Approval by communications director or admin
- ROI estimate calculated:
  - Expected engagement rate × benefit value

**Parent Communication Gate:**
- All parent-student communication must be reviewed by staff
