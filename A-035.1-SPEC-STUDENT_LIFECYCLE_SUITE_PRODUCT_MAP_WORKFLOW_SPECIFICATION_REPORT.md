## 4. Suite Identity

Suite name:

- `Student Lifecycle Suite`

Internal tagline:

- `From applicant to student profile, enrollment, academic record, degree progress, intervention, and graduation readiness.`

Internal description:

- Student Lifecycle Suite is the student operating layer of SBS UB. It connects applicant intake, student profile, enrollment, academic records, transcript preview, degree progress, student requests, appeals, interventions, and graduation readiness into one governed lifecycle.

This is NOT:

- not an LMS
- not a production SIS replacement

- product map and workflow specification
- the next vertical after Executive Governance Suite

## 5. Selected Module Scope

### 5.1 admissions

- product purpose: record applicant intake and admission-review workflow metadata
- included capability: applicant submission states, review checkpoints, additional-info requests, decision metadata, audit trail
- excluded capability: autonomous admission decision, government sync, official acceptance document issuance
- lifecycle or state needs: draft, submitted, under review, additional info requested, decision metadata, accepted, rejected, deferred
- key roles: Admissions Officer, Department Director / Dean, Internal Auditor, Platform Admin
- sensitive boundary: decision metadata only with explicit human review required
- future backend contract need: applicant review workflow, decision metadata schema, status history, audit events
- future frontend surface need: applicant registry and admissions review dashboard
- E2E relevance: applicant registry load, admission review flow visibility, no autonomous decision assertions

### 5.2 applicant_management

- product purpose: maintain applicant records, document metadata, and status history before conversion to student profile
- included capability: applicant profile metadata, document metadata, request-for-more-info, applicant status history
- excluded capability: real personal data imports, live identity verification, live provider sync
- lifecycle or state needs: draft, submitted, under review, awaiting applicant response, accepted, archived
- key roles: Admissions Officer, Student / Applicant, Internal Auditor, Platform Admin
- sensitive boundary: no real applicant data in demo or seed context; metadata-only posture
- future backend contract need: applicant entity, document metadata, status history, controlled mutation rules
- future frontend surface need: applicant registry, applicant detail, additional-info workflow
- E2E relevance: applicant registry and applicant-to-student flow visibility

### 5.3 student_profile

- product purpose: create and maintain governed student profile metadata after admission
- included capability: profile metadata, status history, program assignment links, student identity metadata
- excluded capability: real identity store, credential issuance, national-ID sync
- lifecycle or state needs: profile pending, created, active, suspended, withdrawn, archived
- key roles: Registrar, Academic Advisor, Student Affairs Officer, Internal Auditor, Platform Admin
- sensitive boundary: no real student personal data; role-gated profile access only
- future backend contract need: student profile, identity metadata, program assignment, status history, audit events
- future frontend surface need: student registry and student profile detail
- E2E relevance: student registry load and student profile detail load

### 5.4 enrollment

- product purpose: track program, term, and course enrollment states
- included capability: term activation, enrollment drafts, course selection pending, registrar review, enrollment status changes
- excluded capability: live SIS replacement claim, automatic registration sync, financial clearance automation
- lifecycle or state needs: term activated, draft, submitted, registrar review, enrolled, changed, withdrawn, suspended
- key roles: Registrar, Academic Advisor, Department Director / Dean, Student / Applicant, Internal Auditor
- sensitive boundary: all status changes must be audit-backed and human-controlled
- future backend contract need: enrollment term, student enrollment, course enrollment, status history, review entity
- future frontend surface need: enrollment dashboard and status-detail surfaces
- E2E relevance: enrollment dashboard load and visible transition states

### 5.5 academic_records

- product purpose: store governed academic-record metadata and course-result history
- included capability: record entries, metadata imports or entry flags, review state, status trail
- excluded capability: fake grades, unofficial data silently treated as official, provider sync claims
- lifecycle or state needs: record opened, results entered metadata, record reviewed, locked review state
- key roles: Registrar, Faculty Member, Department Director / Dean, Internal Auditor
- sensitive boundary: academic-record access is high sensitivity and audit-backed
- future backend contract need: academic record, record entry, course-result metadata, review process, audit events
- future frontend surface need: academic-record registry and review surface
- E2E relevance: academic-record route load and review-state visibility

### 5.6 transcript

- product purpose: provide transcript preview and transcript request metadata under strict unofficial boundaries
- included capability: preview state, request metadata, review state, status history, unofficial labeling
- excluded capability: fake official transcript, digital signature, official issuance, auto-issued transcript
- lifecycle or state needs: preview generated, review required, unofficial transcript available, official request deferred
- key roles: Registrar, Student / Applicant, Internal Auditor, Platform Admin
- sensitive boundary: every transcript surface must say unofficial preview and metadata only where appropriate
- future backend contract need: transcript preview, request metadata, output metadata, review state, audit events
- future frontend surface need: transcript preview and request metadata surfaces
- E2E relevance: transcript route with unofficial preview label and no-fake-transcript assertions

### 5.7 degree_progress

- product purpose: show degree-requirement mapping and progress visibility from available sources
- included capability: requirement mapping, progress snapshots, incomplete-data flags, advisor review, readiness draft

## 7. Lifecycle State Model

Suite-wide state model principles:

- every module uses explicit named states
- all meaningful transitions require audit events
- human review states must be visible, not implied
- incomplete data must be surfaced as a state, not hidden
- future official outputs remain deferred and separately labeled

Cross-cutting state categories:

- draft
- submitted
- under review
- additional info requested
- human review required
- metadata issued
- active
- changed
- suspended
- withdrawn
- closed
- archived
- source unavailable
- incomplete data

State-model guardrails:

- no silent transition to accepted, enrolled, eligible, or closed without auditable transition logic
- no hidden scoring state
- no provider-synced state
- no official transcript issued state in this spec slice

## 8. Role Model

### Admissions Officer

- responsibilities: manage applicants, admission reviews, additional-info requests, decision metadata
- allowed suite areas: applicants, admissions
- forbidden actions: autonomous acceptance, credential creation, provider sync
- sensitive data boundaries: applicant access only within admissions scope and audit trail
- future permissions: admissions.read, admissions.review, admissions.metadata.write, applicants.read, applicants.manage, applicants.status.update
- workflow involvement: Flow 1

### Registrar

- responsibilities: student profile governance, enrollment review, academic-record oversight, transcript preview governance, graduation-readiness review
- allowed suite areas: students, enrollment, academic records, transcripts, degree progress, graduation readiness, requests, appeals
- forbidden actions: hidden score assignment, autonomous graduation approval, fake transcript issuance
- sensitive data boundaries: student records limited to operational necessity and audit review
- future permissions: students.read, students.profile.manage, students.status.update, enrollment.read, enrollment.manage, enrollment.review, records.read, records.manage, transcript.preview, degree_progress.read, graduation_readiness.review
- workflow involvement: Flows 2, 3, 4, 5

### Academic Advisor

- responsibilities: advise on student profile context, degree progress, intervention planning, readiness review
- allowed suite areas: students, enrollment, degree progress, interventions, success visibility, requests
- forbidden actions: autonomous adverse action, official transcript issuance, appeal auto-resolution
- sensitive data boundaries: limited access to advisory context and support notes
- future permissions: students.read, degree_progress.read, degree_progress.review, graduation_readiness.review, interventions.read, interventions.manage, success_visibility.read, requests.read
- workflow involvement: Flows 2, 4, 5, 6

### Department Director / Dean

- responsibilities: oversight on admissions, appeals, degree and readiness reviews, escalated decisions
- allowed suite areas: admissions, enrollment review, appeals, degree progress, graduation readiness
- forbidden actions: hidden ranking, discriminatory scoring, silent adverse decision
- sensitive data boundaries: oversight only where department governance applies
- future permissions: admissions.review, enrollment.review, appeals.review, degree_progress.review, graduation_readiness.review
- workflow involvement: Flows 1, 2, 4, 5

### Faculty Member

- responsibilities: contribute course-result metadata and academic review context where permitted
- allowed suite areas: academic-record contribution, limited student academic context
- forbidden actions: transcript issuance, readiness decision, broad student-profile access
- sensitive data boundaries: minimal academic-context access only
- future permissions: records.read, records.manage under scoped rules
- workflow involvement: Flow 3

### Student Affairs Officer

- responsibilities: manage operational student requests, support workflows, intervention coordination
- allowed suite areas: requests, interventions, selected student-profile context
- forbidden actions: autonomous appeal decision, official academic-record mutation outside scope
- sensitive data boundaries: support-only access, no unnecessary academic-record exposure
- future permissions: requests.read, requests.manage, interventions.read, interventions.manage, success_visibility.read
- workflow involvement: Flows 5 and 6

### Student Support Officer

- responsibilities: support interventions, follow-up actions, student-success visibility, support notes
- allowed suite areas: interventions, success visibility, limited support context
- forbidden actions: punitive action, graduation decisions, admissions decisions
- sensitive data boundaries: support-note access only under explicit role scope
- future permissions: interventions.read, interventions.manage, success_visibility.read
- workflow involvement: Flow 6

### Student / Applicant

- responsibilities: submit applicant data, view own status, submit requests or appeals, view allowed transcript preview and readiness context
- allowed suite areas: own applicant state, own student status, own requests, own appeals, own transcript preview, own readiness view
- forbidden actions: broad registry access, other-student access, status override
- sensitive data boundaries: self-only access
- future permissions: scoped self-service equivalents of applicant and student read plus request submission surfaces
- workflow involvement: Flows 1, 2, 3, 5

### Internal Auditor

- responsibilities: review status history, audit events, evidence metadata, workflow integrity
- allowed suite areas: audit and read-only views across suite domains
- forbidden actions: business-state mutation, override of decisions
- sensitive data boundaries: read-only, auditable access with minimization
- future permissions: audit.read plus scoped read access as required
- workflow involvement: all flows as read-only oversight

### Platform Admin

- responsibilities: configuration oversight, permission administration, safe operational governance
- allowed suite areas: admin and configuration scope, audit visibility, technical oversight
- forbidden actions: fabricate business evidence, bypass human-review boundary in product claims
- sensitive data boundaries: administrative access still constrained by audit and minimization
- future permissions: admin.read, admin.configure, audit.read
- workflow involvement: governance and configuration support, not primary business reviewer

## 10. Domain Entity Map

### Admissions / Applicant

- entities: Applicant, ApplicantProfile, ApplicantStatusHistory, AdmissionReview, AdmissionDecisionMetadata, ApplicantDocumentMetadata
- purpose: capture applicant intake, review flow, documents, and decision metadata under audit
- key relationships: Applicant owns ApplicantProfile and ApplicantDocumentMetadata; AdmissionReview and AdmissionDecisionMetadata reference Applicant; ApplicantStatusHistory records transitions
- tenant scope: tenant-scoped applicant records and review artifacts
- audit requirement: every review and status transition requires audit events
- sensitive-data caution: applicant identity and document metadata are high sensitivity and must avoid real personal data in demo/test contexts

### Student Profile

- entities: StudentProfile, StudentIdentityMetadata, StudentProgramAssignment, StudentStatusHistory
- purpose: represent governed student-profile metadata after applicant conversion
- key relationships: StudentProfile owns identity metadata, program assignments, and status history
- tenant scope: tenant-scoped and RBAC-limited
- audit requirement: creation, assignment, suspension, and withdrawal transitions require audit events
- sensitive-data caution: identity metadata must stay minimal and role-scoped

### Enrollment

- entities: EnrollmentTerm, StudentEnrollment, CourseEnrollment, EnrollmentStatusHistory, EnrollmentReview
- purpose: model program-, term-, and course-enrollment workflow with review checkpoints
- key relationships: StudentEnrollment belongs to StudentProfile and EnrollmentTerm; CourseEnrollment belongs to StudentEnrollment; EnrollmentReview and EnrollmentStatusHistory track transitions
- tenant scope: tenant-scoped enrollment records
- audit requirement: submission, review, enroll, change, withdraw, and suspend transitions require audit events
- sensitive-data caution: enrollment status can affect student access and must not be mutated silently

### Academic Records

- entities: AcademicRecord, AcademicRecordEntry, CourseResultMetadata, TranscriptPreview, TranscriptRequestMetadata
- purpose: represent academic-record entries and transcript preview under unofficial boundaries
- key relationships: AcademicRecord owns record entries and course-result metadata; TranscriptPreview and TranscriptRequestMetadata reference AcademicRecord and StudentProfile
- tenant scope: tenant-scoped academic data
- audit requirement: record review and transcript preview generation require audit events
- sensitive-data caution: grades and transcript previews are high sensitivity and must not overclaim official status

### Degree Progress

- entities: DegreeRequirement, DegreeProgressSnapshot, GraduationReadinessReview, RequirementCompletionMetadata
- purpose: map program requirements to visible progress and readiness review
- key relationships: DegreeProgressSnapshot references StudentProfile and DegreeRequirement; GraduationReadinessReview references progress snapshots and completion metadata
- tenant scope: tenant-scoped requirement and readiness records
- audit requirement: progress recompute, readiness review, and status changes require audit events
- sensitive-data caution: incomplete sources must be surfaced explicitly; no hidden score allowed

### Requests / Appeals

- entities: StudentRequest, StudentRequestReview, StudentAppeal, StudentAppealReview, RequestAppealStatusHistory
- purpose: govern student operational requests and appeal decisions under human review
- key relationships: StudentRequest owns StudentRequestReview; StudentAppeal owns StudentAppealReview; RequestAppealStatusHistory tracks both families of transitions
- tenant scope: tenant-scoped request and appeal records
- audit requirement: submission, review, decision metadata, and closure require audit events
- sensitive-data caution: appeals are high sensitivity and cannot rely on autonomous or hidden ranking logic

### Interventions

- entities: StudentSuccessSignal, InterventionPlan, InterventionFollowUp, StudentSupportNote
- purpose: capture support-oriented visibility, intervention planning, and follow-up metadata
- key relationships: StudentSuccessSignal may link to InterventionPlan; InterventionPlan owns follow-up and support-note artifacts
- tenant scope: tenant-scoped support workflows
- audit requirement: signal registration, plan creation, follow-up, and closure require audit events
- sensitive-data caution: support notes and signals are sensitive and must not become punitive scoring artifacts

### Audit

- entities: StudentLifecycleAuditEvent, StudentLifecycleEvidenceMetadata
- purpose: provide cross-suite status history and evidence metadata
- key relationships: audit events reference business entities across all Student Lifecycle modules; evidence metadata attaches to transitions and reviews
- tenant scope: tenant-scoped audit history
- audit requirement: mandatory for every significant state transition
- sensitive-data caution: audit surfaces must balance traceability with data minimization
