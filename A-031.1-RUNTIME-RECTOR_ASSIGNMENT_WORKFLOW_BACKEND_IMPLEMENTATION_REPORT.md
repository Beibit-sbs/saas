## 6. Security Architecture

### 6.1 Multi-Tenant Isolation

- Every service function calls `validate_tenant_id_provided(tenant_id)` at entry (fail-closed)
- Every resource load uses `assert_resource_belongs_to_tenant(resource, tenant_id, ...)` 
- `tenant_id` stored as `BigInteger` (no FK) on all 10 tables for migration portability
- `int(tenant["id"])` conversion enforced at router → service boundary

### 6.2 RBAC Permissions

20 granular permission constants under `admin.rector_assignments.*`:
- `create`, `read`, `read_all`, `read_department`, `assign`, `accept`
- `report_submit`, `report_review`, `evidence_attach`, `comment`
- `status_change`, `complete`, `return`, `escalate`, `cancel`, `archive`
- `audit_read`, `templates_manage`, `dashboard.read`, `admin`

### 6.3 Transition Guard (IDOR Prevention)

`_assert_transition_allowed(current_status, target_status)` enforces the full transition matrix:
- Terminal states (COMPLETED, CANCELLED, ARCHIVED) have zero valid forward transitions (except archive)
- No arbitrary state jumps permitted
- Raises `DomainValidationError` on any invalid transition

## 12. Architecture Decisions

### 12.1 Shared Engine Pool

The `rector_assignment_session_factory` uses `_admissions_engine`, consistent with all other Wave-20 modules. There is no separate database; all modules share the same PostgreSQL instance and engine pool.

### 12.2 tenant_id as BigInteger (No FK)

`tenant_id` on all 10 tables is a `BigInteger` without a foreign key constraint. This is the established project pattern for migration portability (tenants live in a different schema/service layer).

### 12.3 INSERT-ONLY Audit/History Tables

`rector_assignment_audit_events` and `rector_assignment_status_history` are append-only by design:
- No `update()` queries on these tables in repository.py
- No `delete()` queries in any service function
- Enforces immutable audit integrity

### 12.4 Dashboard Anti-Fake Contract

The dashboard is the most security-sensitive endpoint from a data-integrity perspective:
- Schema default: `fake_metrics: bool = False`
- Schema default: `data_source: str = "computed_from_assignments"`
- Service assertion: `assert result["fake_metrics"] is False`
- Repository: only real SQL COUNT/aggregations used

These three layers create defense-in-depth against accidental metric falsification.
