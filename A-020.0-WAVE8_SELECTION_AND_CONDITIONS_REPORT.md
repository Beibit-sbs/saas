## 7. Selected A-020 Top 5

Selected features for A-020.1-A-020.5:

1. Room Allocation Readiness Contract Stabilization
   - Why selected: the existing context already carries `room_capacity`, `required_capacity`, and `room_allocation_required`, but the contract needs to be stabilized and normalized across scheduling, room booking, and Brain Core.
   - Current maturity: partial, but already proven in A-018.1/A-018.2.
   - Missing pieces: canonical evidence shaping, consistent payload normalization, and explicit contract boundaries for downstream consumers.
   - Modules involved: `scheduling`, `room_booking`, `brain_core`, `platform/kpi`.
   - Reuse: `fetch_scheduling_context()`, room-allocation readiness signals, KPI lineage.
   - Brain role: provide stable evidence for section_conflict / enrollment_capacity_risk decisions.
   - KPI role: ensure room-conflict lineage stays deterministic.
   - Risk: low, because it is a contract stabilization step rather than a new execution path.
   - Expected next step: A-020.1 contract hardening and test coverage.

2. Room Inventory / Room Capability Contract
   - Why selected: scheduling currently knows capacity, building, and room type, but the room capability contract still lacks a richer canonical room inventory shape for allocation reasoning.
   - Current maturity: partial.
   - Missing pieces: richer room capability fields, standard availability/status representation, and consistent room inventory payloads.
   - Modules involved: `room_booking`, `scheduling`, `university_core`, `brain_core`.
   - Reuse: `campus_rooms`, `ClassroomModel`, `RoomType`, room-capacity checks.
   - Brain role: convert room metadata into usable allocation evidence.
   - KPI role: make room-capability signals visible in metrics later, not during apply.
   - Risk: moderate, because capability normalization can expose naming mismatches.
   - Expected next step: A-020.2 inventory/capability contract stabilization.

3. Scheduling Conflict Detection Enhancement
   - Why selected: conflict detection is already present, but A-020 should extend it with clearer room-capability and schedule-conflict evidence instead of jumping to auto-solve behavior.
   - Current maturity: strong backend baseline, but not yet allocation-intelligence complete.
   - Missing pieces: enhanced conflict evidence, richer constraint matrix, and better distinction between detect / recommend / simulate.
   - Modules involved: `scheduling`, `room_booking`, `events_management`, `brain_core`.
   - Reuse: `SchedulingRules.validate_room_capacity`, room conflict checks, `scheduling.room_conflict.detected`, `scheduling.room_allocation.required`.
   - Brain role: keep the signal-to-decision path aligned with existing `section_conflict` scenarios.
   - KPI role: preserve room-conflict lineage into `room_conflict_count` and related cards.
   - Risk: low to moderate; logic exists, but the evidence surface needs tightening.
   - Expected next step: A-020.3 conflict detection enhancement.

4. Capacity Matching Brain
   - Why selected: this is the central brain-domain step that turns room capacity into an explicit recommendation signal without mutating production schedules.
   - Current maturity: brain-ready, but the allocation brain is not yet a distinct recommendation layer.
   - Missing pieces: ranked match logic, room-capacity fit scoring, and explicit non-destructive outputs.
   - Modules involved: `brain_core`, `scheduling`, `room_booking`, `platform/kpi`.
   - Reuse: `fetch_scheduling_context()`, `SignalRegistry`, `DecisionRegistry`, classifier paths for scheduling room signals.
   - Brain role: score candidate rooms and produce recommendation evidence only.
   - KPI role: surface allocation pressure and fit quality later, without auto-apply.
   - Risk: moderate; requires careful guardrails to avoid drifting into optimizer scope.
   - Expected next step: A-020.4 capacity matching brain.

5. Room Allocation Recommendation Engine
   - Why selected: recommendation is the safest useful output for A-020 because it gives admins evidence and ranked options without mutating the timetable.
   - Current maturity: not yet implemented as a dedicated layer, but all upstream evidence is already present.
   - Missing pieces: deterministic ranking, evidence payload, approval-friendly output format, and explicit no-mutation behavior.
   - Modules involved: `brain_core`, `scheduling`, `room_booking`, `dashboard`, `platform/kpi`.
   - Reuse: room-capacity evidence, conflict signals, KPI lineage, dashboard cards.
   - Brain role: publish recommendations, not apply changes.
   - KPI role: expose recommendation pressure and fit evidence in A-020.6.
   - Risk: moderate; the main hazard is scope creep into simulation/apply behavior.
   - Expected next step: A-020.5 recommendation engine.

Notes on exclusions:
- `Auto-Redistribution Simulation Mode` is a good follow-on candidate, but it is intentionally deferred until the contract and recommendation layers are stable.
- `Human-approved Timetable Change Workflow` is already partly covered by existing approval/reschedule mechanics and should not become the primary A-020.1-A-020.5 focus.

## 9. Scheduling Automation Safety Model

Default target for A-020: Level 2 to Level 3.

- Level 1 — Detect
  - detect conflicts
  - detect capacity mismatch
  - detect equipment mismatch
  - detect room double-booking
- Level 2 — Recommend
  - suggest candidate rooms
  - rank rooms by capacity, equipment, and availability
  - provide evidence for humans
- Level 3 — Simulate
  - simulate timetable changes
  - show conflicts resolved or created
  - no production mutation
- Level 4 — Human-approved apply
  - admin reviews and approves
  - system applies only safe, bounded changes
- Level 5 — Restricted auto-apply
  - disabled by default
  - requires explicit policy flag
  - not part of A-020 unless a later wave explicitly authorizes it

## 10. Non-destructive Scheduling Policy

A-020 must preserve the following guarantees:
- no automatic mass room reassignment without approval
- no automatic destructive timetable changes
- no unapproved teacher or group schedule changes
- no silent override of room booking constraints
- no cross-tenant timetable leakage
- no fake optimization result presented as authoritative
- no production mutation without a human-reviewed path

The current codebase already supports this posture: scheduling emits conflict and capacity signals, room booking emits allocation-needed evidence, and Brain Core routes those signals into existing review-oriented scenarios.
