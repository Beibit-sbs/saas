# A-035.2-SPEC - Student Lifecycle Suite Backend Domain / DB / API Contract Report

## 1. Executive Summary

A-035.2-SPEC defines the backend implementation contract for Student Lifecycle Suite. It specifies the future backend module structure, database table contract, enums and lifecycle states, schema surface, repository responsibilities, service responsibilities, router and API shape, permissions, audit model, dashboard contract, runtime subset recommendation, backend test plan, and runtime validation gates. This is a spec-only and docs-only action. No backend runtime, frontend runtime, migrations, models, routes, tests, transcripts, or provider integrations are created.

- `/api/admin/student-lifecycle`

Permissions namespace:

- `student_lifecycle.*`

Table prefix:

- `sl_`

Module strategy principles derived from existing repo patterns:

- keep router thin and service-oriented, matching the Document Workflow OS pattern
- keep permissions centralized in `permissions.py`
- use tenant dependency injection and fail-closed tenant lookups in `dependencies.py`
- keep repository DB-only with no business decisions or provider calls
- keep service responsible for lifecycle enforcement, anti-fake constraints, and audit generation
- keep schemas explicit about `human_review_required`, `automated_decision = false`, `provider_integration_enabled = false`, `fake_metrics = false`, and limitations
- keep audit and status-history behavior explicit rather than implied by generic helpers

## 5. Database Table Contract

Selected DB table contract count: `35`

All tables must include:

- `tenant_id` required
- synthetic primary key
- `created_at`
- `updated_at`
- `archived_at` or equivalent soft-archive field where relevant
- no hard delete runtime path
- audit-event creation on significant status changes
- no requirement for real personal data in test or demo fixtures

### Applicant / Admissions Tables

#### 1. `sl_applicants`

- purpose: root applicant record keyed by synthetic applicant identifier
- required tenant_id: yes
- key columns: `id`, `tenant_id`, `applicant_code`, `status`, `human_review_required`, `source_available`, `archived_at`
- foreign keys: none directly required at creation
- status fields: `status` using `ApplicantStatus`
- soft-delete/archive strategy: archive only
- audit/event requirement: `APPLICANT_CREATED`, `APPLICANT_SUBMITTED`, `APPLICANT_STATUS_CHANGED`
- sensitive-data notes: metadata-only identifiers, no real personal data required

#### 2. `sl_applicant_profiles`

- purpose: applicant profile metadata separate from root applicant row
- required tenant_id: yes
- key columns: `applicant_id`, program-interest metadata, entry-term metadata, synthetic contact placeholders, limitation flags
- foreign keys: `applicant_id -> sl_applicants.id`
- status fields: inherit applicant status context
- soft-delete/archive strategy: archive with applicant
- audit/event requirement: profile changes generate audit metadata
- sensitive-data notes: placeholder profile metadata only in tests/demos

#### 3. `sl_applicant_status_history`

- purpose: immutable applicant status transition log
- required tenant_id: yes
- key columns: `applicant_id`, `previous_status`, `new_status`, `actor_user_id`, `reason`, `request_id`, `created_at`
- foreign keys: `applicant_id -> sl_applicants.id`
- status fields: previous/new applicant status
- soft-delete/archive strategy: never hard delete
- audit/event requirement: mirrors audit event stream
- sensitive-data notes: decision rationale must avoid hidden scoring language

#### 4. `sl_admission_reviews`

- purpose: admission review work items
- required tenant_id: yes
- key columns: `applicant_id`, `review_status`, assigned reviewer metadata, due metadata, review notes metadata
- foreign keys: `applicant_id -> sl_applicants.id`
- status fields: `review_status` using `AdmissionReviewStatus`
- soft-delete/archive strategy: close/archive only
- audit/event requirement: `ADMISSION_REVIEW_STARTED`, review status changes
- sensitive-data notes: reviewer notes remain metadata, no autonomous output

#### 5. `sl_admission_decision_metadata`

- purpose: admission decision metadata only, not official admission output
- required tenant_id: yes
- key columns: `applicant_id`, `review_id`, `decision_status`, `decision_note`, `human_review_required`, `automated_decision`, `provider_integration_enabled`
- foreign keys: `applicant_id -> sl_applicants.id`, `review_id -> sl_admission_reviews.id`
- status fields: tied to applicant and review state
- soft-delete/archive strategy: immutable or append-only preferred
- audit/event requirement: `ADMISSION_DECISION_METADATA_RECORDED`
- sensitive-data notes: no official offer letter or provider-sync claim

#### 6. `sl_applicant_document_metadata`

- purpose: applicant document metadata registry
- required tenant_id: yes
- key columns: `applicant_id`, `document_type`, `document_ref`, `source_available`, `limitations`
- foreign keys: `applicant_id -> sl_applicants.id`
- status fields: optional document review status if needed later
- soft-delete/archive strategy: archive with applicant
- audit/event requirement: evidence attachment events where relevant
- sensitive-data notes: metadata only, not real file contents in demo/test scope
