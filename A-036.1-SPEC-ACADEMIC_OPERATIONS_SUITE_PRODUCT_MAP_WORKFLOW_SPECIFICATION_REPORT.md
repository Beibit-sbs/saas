## 4. Suite Identity

Suite name: Academic Operations Suite.

Tagline:

From curriculum and timetable to attendance, teaching load, exams, grades, and academic operations visibility.

Internal description:

Academic Operations Suite is the operational academic layer of SBS UB. It connects curriculum, course catalog, academic calendar, timetable, classroom and room allocation, attendance, teaching load, exam planning, gradebook metadata, academic policy exceptions, and academic operations visibility into one governed academic workflow.

This is not:

- not an LMS
- not a fake gradebook
- not an automated grading system
- not an automated exam decision system
- not an automatic student sanction system
- not a biometric attendance system
- not a production SIS replacement
- not Platonus integration
- not provider integration
- not production-ready
- not sales-ready
- not GCC-ready
- not L5/L6

This is:

- a product map and workflow specification
- the third major product vertical after Executive Governance Suite and Student Lifecycle Suite
- the planning foundation for backend/API contract definition
- the academic operations layer for SBS UB University OS

## 5. Selected Module Scope

1. `curriculum_management`
   - product purpose: manage curriculum metadata, versions, requirements, and review status
   - included capability: curriculum draft/review/approved-metadata states; curriculum-to-course mapping metadata
   - excluded capability: official curriculum approval execution; ministry/provider sync
   - lifecycle/state needs: draft, submission, review, approved metadata, archive
   - key roles: Vice Rector for Academic Affairs, Registrar, Program Chair, Academic Quality Officer, Internal Auditor
   - sensitive boundary: no fake official curriculum approval
   - future backend contract need: curriculum, version, and mapping entities with audit-backed transitions
   - future frontend surface need: curriculum registry, detail, version comparison, review queue
   - E2E relevance: curriculum draft-to-review-to-approved-metadata journey

2. `course_catalog`
   - product purpose: expose course catalog metadata linked to curriculum and academic terms
   - included capability: course metadata, prerequisites, credits, term availability metadata
   - excluded capability: official external publication claim
   - lifecycle/state needs: draft, review required, published metadata, term linked, archive
   - key roles: Registrar, Program Chair, Academic Quality Officer, Internal Auditor
   - sensitive boundary: metadata-only until official source exists

## 6. Core Product Flows

Flow 1 - Curriculum to Course Catalog

- lifecycle: Curriculum Draft -> Curriculum Submitted for Review -> Curriculum Review Required -> Curriculum Approved Metadata -> Course Catalog Draft -> Course Catalog Review Required -> Course Catalog Published Metadata -> Academic Term Linked -> Archived
- roles: Vice Rector for Academic Affairs, Registrar, Program Chair, Academic Quality Officer, Internal Auditor, Platform Admin
- boundaries: no fake official curriculum approval, no fake official course catalog publication, metadata only, human review required, audit-backed transitions

Flow 2 - Academic Calendar to Timetable

- lifecycle: Academic Term Draft -> Academic Calendar Draft -> Calendar Review Required -> Calendar Approved Metadata -> Timetable Draft -> Room Allocation Pending -> Conflict Review Required -> Timetable Published Metadata -> Archived
- roles: Registrar, Timetable Coordinator, Department Director / Dean, Program Chair, Platform Admin
- boundaries: no automatic final scheduling, no fake room availability, no provider or SIS sync claim, conflict review required, human review required

Flow 3 - Teaching Load and Faculty Assignment

- lifecycle: Teaching Load Draft -> Department Review Required -> Faculty Assignment Metadata -> Workload Conflict Flagged -> Human Review Required -> Approved Metadata -> Archived
- roles: Vice Rector for Academic Affairs, Department Director / Dean, Program Chair, Faculty Member, Internal Auditor
- boundaries: no automatic faculty workload decision, no hidden faculty score, no faculty performance score, no HR decision automation, no discriminatory ranking

Flow 4 - Attendance Operations

- lifecycle: Attendance Session Planned -> Attendance Collection Pending -> Attendance Metadata Recorded -> Exception Review Required -> Attendance Summary Available -> Audit Archived
- roles: Faculty Member, Student Affairs Officer, Registrar, Department Director / Dean, Internal Auditor
- boundaries: no fake attendance, no biometric attendance claim, no automatic student sanction, no punitive automation, exception review required, human review required

Flow 5 - Exam Planning and Gradebook Metadata

- lifecycle: Exam Plan Draft -> Exam Schedule Review Required -> Exam Room Allocation Metadata -> Gradebook Metadata Opened -> Grade Entry Metadata Recorded -> Grade Review Required -> Grade Publication Metadata -> Archived
- roles: Exam Office Coordinator, Registrar, Faculty Member, Program Chair, Academic Quality Officer, Internal Auditor
- boundaries: no fake exams, no fake grades, no automated grading, no official grade publication claim, no exam outcome automation, human review required

Flow 6 - Academic Operations Visibility

- lifecycle: Dashboard Computed from Available Metadata -> Incomplete Data Flagged -> Conflict Queue Visible -> Human Review Queue Visible -> Audit Evidence Available -> Export Metadata Prepared
- roles: Vice Rector for Academic Affairs, Registrar, Department Director / Dean, Academic Quality Officer, Internal Auditor, Platform Admin
- boundaries: fake_metrics=false, no invented academic KPI, no hidden score, no autonomous decision, incomplete_data=true where needed, limitations[] visible

## 10. Domain Entity Map

Curriculum / Course Catalog

- `AcademicCurriculum`, `CurriculumVersion`, `CurriculumCourseMapping`, `CourseCatalogEntry`, `CourseCatalogTermLink`
- purpose: hold curriculum structure, course alignment, and catalog-term metadata
- tenant scope: tenant-scoped academic configuration and metadata only
- key relationships: curriculum versions map to course catalog entries and term links
- lifecycle state: draft, review, approved/published metadata, archive
- audit requirement: every transition and mapping change must be audit-backed
- sensitive-data caution: no official approval or publication claims without future authoritative source

Academic Calendar / Timetable

- `AcademicTerm`, `AcademicCalendarEntry`, `TimetablePlan`, `TimetableSlot`, `TimetableConflict`, `RoomAllocation`, `RoomCapacityMetadata`
- purpose: model term timing, schedule planning, room usage, and conflict visibility
- tenant scope: tenant-scoped operational planning and review metadata
- key relationships: terms contain calendar entries; timetable plans and slots depend on terms and room allocations; conflicts reference plan/slot/allocation context
- lifecycle state: term draft through published metadata and archive
- audit requirement: conflict generation, review, and publish-metadata steps must be recorded
- sensitive-data caution: no fake room availability and no automatic schedule decisions

Attendance

- `AttendanceSession`, `AttendanceMetadata`, `AttendanceExceptionReview`, `AttendanceSummary`
- purpose: capture attendance session metadata and exception-review flow
- tenant scope: tenant-scoped attendance operations with review-bound access
- key relationships: sessions own metadata records, summaries, and exception reviews
- lifecycle state: planned, pending, metadata recorded, exception review, summary, audit archive
- audit requirement: metadata entry, review, and summary generation require auditable events
- sensitive-data caution: no biometric claims, no punitive automation, no fake attendance

Teaching Load / Faculty Assignment

- `TeachingLoadPlan`, `TeachingLoadAssignment`, `FacultyAssignmentMetadata`, `WorkloadConflict`
- purpose: model workload planning, assignments, and reviewable conflicts
- tenant scope: tenant-scoped faculty-assignment operations
- key relationships: plans contain assignments and conflict records; assignment metadata links load and faculty visibility
- lifecycle state: draft through approved metadata and archive
- audit requirement: assignment and conflict transitions must be logged
- sensitive-data caution: no hidden faculty score, no performance ranking, no HR automation

Exam / Gradebook

- `ExamPlan`, `ExamScheduleMetadata`, `ExamRoomAllocation`, `GradebookMetadata`, `GradeEntryMetadata`, `GradeReviewMetadata`
- purpose: manage exam and gradebook workflow metadata without implying official outcomes
- tenant scope: tenant-scoped exam and gradebook operations
- key relationships: exam plans connect to schedule metadata and room allocations; gradebook metadata links to grade entry/review metadata
- lifecycle state: draft/review/published metadata or review/publication metadata states
- audit requirement: all review and publication-metadata transitions must be traceable
- sensitive-data caution: no fake grades, no automated grading, no official publication claim

Policy Exceptions

- `AcademicPolicyException`, `AcademicPolicyExceptionReview`, `AcademicPolicyExceptionStatusHistory`
- purpose: track exception requests, reviews, and status history
- tenant scope: tenant-scoped exception governance
- key relationships: exceptions own reviews and status-history records
- lifecycle state: draft, submitted, review required, decision metadata recorded, response issued, closed, archived
- audit requirement: every review decision and status step must be evidence-backed
- sensitive-data caution: no automatic approval and no hidden scoring logic

Dashboard / Audit / Evidence

- `AcademicOperationsDashboardSnapshot`, `AcademicOperationsAuditEvent`, `AcademicOperationsEvidenceMetadata`
- purpose: capture cross-module visibility, audit history, and evidence attachments
- tenant scope: tenant-scoped summary and audit layer
- key relationships: snapshots aggregate across modules; audit events and evidence metadata support transitions and dashboard limitations
- lifecycle state: computed summaries and immutable audit/evidence records
- audit requirement: full audit lineage for workflow transitions and dashboard export metadata
- sensitive-data caution: fake_metrics=false, limitations[] visible, incomplete-data flags preserved
