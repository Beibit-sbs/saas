# A-055.GRD-R1 Hardening — Grade / Transcript Integrity Review Remediation Report

## Scope

Remediate confirmed findings from the adversarial review of the grades write +
GPA/transcript read chain. The review produced 15 findings, each independently
verified (default-refute). **11 confirmed, 4 refuted.** Two confirmed findings are
HIGH grade-integrity defects; the rest are MEDIUM/LOW and are documented below for
follow-up.

## HIGH-A — dropped/withdrawn grades corrupted GPA and the transcript (F1/F6/F8)

**Confirmed.** `grade_code`/`grade_points` are deliberately **retained** on an
enrollment when it is dropped or withdrawn (the audit trail keeps the historical
grade — `enrollments/service.py` drop/withdraw paths do not clear them). But the
aggregation queries had **no enrollment-status filter**:

- `GradeLifecycleService.calculate_student_gpa` filtered only `tenant_id`,
  `student_profile_id`, `grade_points IS NOT NULL` — so a graded-then-dropped
  enrollment still contributed its grade points and credits to the weighted GPA.
- `GradeLifecycleService.get_student_transcript` likewise listed every enrollment,
  inflating `total_credits` and showing dropped courses as earned.
- `TranscriptService._load_enrollments` (which feeds `generate_transcript`, the
  persisted `TranscriptRecordModel` rows, **and** the consistency report) had the
  same gap, so the corruption was written through to stored transcripts.

A student who earned an A, then dropped the course, kept the A in their GPA and
transcript — a silent academic-record integrity violation.

**Fix:** added a module constant
`_NON_CREDIT_BEARING_STATUSES = (EnrollmentStatus.DROPPED, EnrollmentStatus.WITHDRAWN)`
and an `enrollment_status NOT IN (...)` predicate to all three aggregation queries
(`calculate_student_gpa`, `get_student_transcript`, `TranscriptService._load_enrollments`).
Statuses are compared as enum members (matching the existing `.in_()` idiom in
`enrollments/service.py`), so binding stays consistent with how the column is stored.

## HIGH-B — change_grade bypassed the term-window and section lock (F2/F3/F5)

**Confirmed.** `submit_grade` enforced two cross-entity integrity guards —
`_check_term_submission_window_open` (no retroactive grading after the term's
end_date + grace period) and `_check_section_not_cancelled` — but `change_grade`
enforced **neither**. A regrade could therefore rewrite a grade on a closed term or
a cancelled section even though the original submission was blocked, corrupting an
already-issued transcript past the census deadline.

**Fix:** `change_grade` now calls `_check_section_not_cancelled` and
`_check_term_submission_window_open` immediately after loading the enrollment,
exactly as `submit_grade` does. A blocked change raises `DomainValidationError`
(router → 400) and persists nothing.

## Tests

- `test_calculate_student_gpa_excludes_dropped_and_withdrawn` — the GPA aggregation
  query compiles with an `enrollment_status NOT IN` predicate; the exclusion
  constant is `(DROPPED, WITHDRAWN)`. (Mock harness can't run SQL, so the WHERE
  clause is asserted at the compiled-statement level — the strongest unit-level
  proof available here.)
- `test_get_student_transcript_excludes_dropped_and_withdrawn` — same predicate on
  the transcript row query.
- `test_change_grade_blocked_after_term_submission_window_closes` — a change against
  a term whose window has closed raises `DomainValidationError` and `commit` is
  never called.
- Updated `test_change_grade_success` / `test_change_grade_optimistic_lock_conflict`
  to monkeypatch the two new guards (mirroring the existing `submit_grade` tests),
  since change_grade now exercises them.

### Bonus — fixed a pre-existing RED test in the same module

`test_get_student_transcript_records_read_usage` was **already failing on clean
HEAD** (verified via `git stash`): its mocked `execute.side_effect` ordering
predated the `_load_enrollments` + consistency-report calls that
`get_student_transcript` now makes, so the student lookup consumed the wrong mock
and raised `TenantResourceNotFoundError`. Corrected the mock sequence
(student → enrollments → records → course → term) with an enrollment that matches
the cached record so the cached-records path is exercised. Not caused by this
change, but cleared while in the same file.

## Confirmed but deferred (documented, not silently dropped)

- **F4 / F11 (MEDIUM) — idempotent-replay divergence:** `change_grade`'s
  early-return idempotent replay compares `(grade_code, grade_points)` but skips the
  new guards on the replay path; a replay after a window close still short-circuits
  to success. Low blast radius (no state change) but inconsistent; harden later.
- **F7 (MEDIUM) — transcript GET performs writes:** `get_student_transcript`
  auto-heals by calling `generate_transcript`, which persists `TranscriptRecordModel`
  rows on a read path. Intentional self-healing, but a GET with write side effects is
  a design smell worth isolating behind an explicit endpoint.
- **F9 (LOW) — `create_grading_scale` has no direct test.**
- **F10 (LOW) — ABAC ownership check on `change_grade`** (`validate_grade_modification`)
  is advisory in some configs; confirm it is binding under production policy.

## Refuted (4)

Tenant scoping on GPA/transcript (queries ARE tenant-filtered, including a
course-tenant cross-check); a duplicate framing of the status-filter finding; and
two over-broad claims already covered by existing version/optimistic-lock handling.

## Lesson (reinforced)

Same theme as the finance-acknowledge and hardship-gate bugs: the suite proved
*structure and in-order happy paths* but never the integrity-violating path. A grade
that survives a drop, and a regrade that beats the census lock, both shipped green
because no test submitted-then-dropped, or changed-after-close. Read aggregations and
"change" mutations need the same negative coverage as the primary write.
