## Section 6 — Candidate Expansion Options

### Option A — Notifications / Outbox Foundation

**Purpose**: Create an internal outbox table for assignment lifecycle notification intents.
Dispatcher is NOT implemented in first runtime. Events are created as PENDING/READY only.

**Trigger events** (assignment lifecycle):
- Assignment created
- Assignment assigned to executor
- Assignment accepted by executor
- Report submitted
- Assignment returned for revision
- Assignment completed
- Assignment escalated
- Overdue detected (policy-driven or scheduled check)
- Comment added
- Evidence/attachment added

**Constraints**:
- No live email/SMS send
- No external provider call
- No webhook dispatch
- PENDING/READY status only in first runtime
- Every outbox row requires corresponding audit event
- Cross-tenant outbox read prohibited

### Option B — SLA / Overdue / Escalation Policy

**Purpose**: Introduce tenant-configurable SLA policy entities. Formalize overdue detection
beyond simple `due_date < today`. Introduce escalation policy configuration.

**Existing foundation**:
- `is_overdue: bool` computed in `RectorAssignment`
- `due_date` field
- `overdue_only` filter in `repo_list_assignments()`
- `escalation_level` in `RectorAssignmentEscalation`

**New policy entities**:
- `rector_assignment_sla_policies` — per-tenant SLA configuration
- `rector_assignment_escalation_policies` — escalation level configuration

**Constraints**:
- Overdue derived from `due_date` and active status; not stored unless snapshot justified
- Due-soon is computed at query time
- Escalation first runtime: prefer queued event + manual confirmation
- No punitive action
- No grade/student/faculty record impact
- No hidden ranking

### Option C — Reporting / Dashboard Expansion

**Purpose**: Add deeper analytics to the existing `DashboardSummaryResponse`. All new fields
computed from source DB. `fake_metrics = False` mandatory.

**Current dashboard fields** (already implemented, A-031.1-RUNTIME):

- `completed_count`, `cancelled_count`, `report_submitted_count`, `returned_count`

- `completion_rate_30d`, `average_days_to_complete`
- `by_status: dict[str, int]`, `by_priority: dict[str, int]`
- `by_unit: list[UnitCountEntry]`
- `top_overdue: list[dict]`
- `data_source = "computed_from_assignments"`, `fake_metrics = False`

**New fields to specify for A-031.5-RUNTIME** (not yet implemented):

## Section 8 — Notification / Outbox Contract

### Table: `rector_assignment_outbox_events`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | BIGSERIAL | PRIMARY KEY | Auto-increment |
| `tenant_id` | BIGINT | NOT NULL, FK → app_tenants(id) | Tenant isolation mandatory |
| `assignment_id` | BIGINT | NOT NULL, FK → rector_assignments(id) | Source assignment |
| `event_type` | VARCHAR(100) | NOT NULL | See event types below |
| `recipient_user_id` | BIGINT | NULLABLE, FK → app_local_users | Specific recipient; NULL = role-broadcast |
| `recipient_role` | VARCHAR(100) | NULLABLE | Role-based broadcast; mutually exclusive with `recipient_user_id` |
| `channel` | VARCHAR(20) | NOT NULL, CHECK IN ('IN_APP','EMAIL','SMS') | Delivery channel intent |
| `payload_json` | JSONB | NOT NULL, DEFAULT '{}' | Event payload; no secrets |
| `status` | VARCHAR(20) | NOT NULL, DEFAULT 'PENDING', CHECK IN ('PENDING','READY','DISPATCHED','FAILED','CANCELLED') | First runtime: PENDING/READY only |
| `retry_count` | INT | NOT NULL, DEFAULT 0 | Dispatch retry metadata |
| `next_retry_at` | TIMESTAMPTZ | NULLABLE | Retry scheduling metadata |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | Creation timestamp |
| `updated_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | Last update |

### Indexes Required

```sql
CREATE INDEX ix_rao_tenant_assignment ON rector_assignment_outbox_events (tenant_id, assignment_id);
CREATE INDEX ix_rao_tenant_status ON rector_assignment_outbox_events (tenant_id, status);
CREATE INDEX ix_rao_tenant_event_type ON rector_assignment_outbox_events (tenant_id, event_type);
```

### Outbox Event Types

| Event Type | Trigger | Recipient Target |
|---|---|---|
| `rector_assignment.created` | Assignment INSERT | Controller/supervisor role |
| `rector_assignment.assigned` | Status → ASSIGNED | Executor user |
| `rector_assignment.accepted` | Status → ACCEPTED | Controller role |
| `rector_assignment.report_submitted` | Status → REPORT_SUBMITTED | Controller/rector role |
| `rector_assignment.returned_for_revision` | Status → RETURNED | Executor user |
| `rector_assignment.completed` | Status → COMPLETED | Originator/controller |
| `rector_assignment.escalated` | Escalation created | Rector/prorector role |
| `rector_assignment.overdue_detected` | Due date check (policy or scheduled) | Executor + controller |
| `rector_assignment.comment_added` | Comment INSERT | Assignment owner/executor |
| `rector_assignment.evidence_attached` | Evidence INSERT | Controller role |

### Outbox Status Lifecycle

```
PENDING → READY → DISPATCHED
          ↓
        FAILED → retry → READY
PENDING → CANCELLED (manual or business rule)
```

**First runtime constraint**: Only PENDING and READY statuses written. DISPATCHED/FAILED/CANCELLED
reserved for future dispatcher runtime (A-031.6 or A-031.5-RUNTIME if expanded).

### Outbox Safety Rules

1. Every outbox event creation MUST have a corresponding `rector_assignment_audit_events` row.
2. No outbox row may cause a status transition on the assignment.
3. No outbox row may reveal cross-tenant assignment data in `payload_json`.
4. `payload_json` MUST NOT contain passwords, tokens, or PII beyond display name.
5. Outbox list/read endpoints MUST be scoped by `tenant_id`.
6. No DISPATCHED/FAILED transition until a safe dispatcher is implemented and audited.

## Section 9 — SLA / Overdue Policy Contract

### Table: `rector_assignment_sla_policies`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | BIGSERIAL | PRIMARY KEY | |
| `tenant_id` | BIGINT | NOT NULL, FK → app_tenants(id) | Tenant isolation |
| `name` | VARCHAR(200) | NOT NULL | Policy label |
| `priority` | VARCHAR(20) | NULLABLE, CHECK IN ('NORMAL','HIGH','URGENT','CRITICAL') | Assignment priority this applies to |
| `due_days` | INT | NOT NULL, ge=1 | Default due days from assignment creation |
| `warning_before_hours` | INT | NOT NULL, DEFAULT 48 | Hours before due_date to flag "due soon" |
| `overdue_after_hours` | INT | NOT NULL, DEFAULT 0 | Hours past due_date before classified overdue (0 = immediate) |
| `escalation_after_hours` | INT | NOT NULL, DEFAULT 72 | Hours overdue before escalation recommended |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | Active policy flag |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | |
| `updated_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | |

### Table: `rector_assignment_escalation_policies`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | BIGSERIAL | PRIMARY KEY | |
| `tenant_id` | BIGINT | NOT NULL, FK → app_tenants(id) | Tenant isolation |
| `assignment_priority` | VARCHAR(20) | NOT NULL | NORMAL/HIGH/URGENT/CRITICAL |
| `escalation_level` | INT | NOT NULL, ge=1, le=4 | Maps to existing escalation_level (1-4) |
| `escalate_to_role` | VARCHAR(100) | NOT NULL | RBAC role to escalate to |
| `escalate_after_hours` | INT | NOT NULL, ge=1 | Hours overdue before this level triggers |
| `require_manual_confirmation` | BOOLEAN | NOT NULL, DEFAULT TRUE | Must a human confirm escalation action? |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | |
| `updated_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | |

### SLA Computation Rules

| Field | Computation | Notes |
|---|---|---|
| `due_soon` | `due_date` - NOW() < `warning_before_hours` AND NOT overdue | Computed at query time; not stored |
| `is_overdue` | `due_date` < (NOW() - `overdue_after_hours`) AND active status | Extends existing `is_overdue` bool |
| `overdue_hours` | EXTRACT(EPOCH FROM (NOW() - `due_date`)) / 3600 | Derived; for aging bucket computation |
| Escalation trigger | `overdue_hours` >= `escalation_after_hours` for applicable policy | Queue escalation event; require confirmation |

### SLA Policy Rules

1. Per-tenant only; no global/cross-tenant SLA policy.
2. If no active SLA policy matches assignment priority, fall back to module default
   (due_days=14, warning_before_hours=48, overdue_after_hours=0, escalation_after_hours=72).
3. SLA policy affects `due_date` suggestion at assignment creation; not retroactive unless
   explicitly re-applied.
4. Policy update MUST emit audit event.
5. Policy delete MUST be soft-delete (is_active=False), not hard delete.
6. No punitive action, no grade impact, no student record impact.

## Section 10 — Escalation Policy Contract

### Escalation Rules

1. Escalation is a recommendation / event queue, not an automatic punitive action.
2. First runtime: `require_manual_confirmation = True` by default.
3. Escalation event creation MUST emit `rector_assignment_audit_events` row.
4. Escalation outbox event MUST be created when escalation fires.
5. Escalation level must follow sequence (cannot skip levels without explicit override).
6. No autonomous decision on assignment outcome.
7. Escalation to rector/prorector role requires separate RBAC permission check.
8. Cross-tenant escalation is forbidden.

### Escalation Levels (maps to existing `escalation_level INT 1-4`)

| Level | Default Role | Trigger |
|---|---|---|
| 1 | CONTROLLER | First overdue detection |
| 2 | PRORECTOR | Level 1 unresolved after `escalate_after_hours` |
| 3 | RECTOR | Level 2 unresolved |
| 4 | PLATFORM_ADMIN | Level 3 unresolved (exceptional only) |

## Section 11 — Reporting / Dashboard Expansion Contract

### New Dashboard Fields (to be added to `DashboardSummaryResponse`)

All fields MUST be computed from source DB. `fake_metrics` MUST remain `False`. If computation
fails for any field, the field MUST return `null` or `incomplete_data` flag rather than a
fabricated zero.

#### `overdue_aging_buckets: OverdueAgingBuckets`

```python
class OverdueAgingBuckets(BaseModel):
    days_1_3: int      # Overdue 1-3 days
    days_4_7: int      # Overdue 4-7 days
    days_8_14: int     # Overdue 8-14 days
    days_15_plus: int  # Overdue 15+ days
```

Computed from: `due_date` and NOW() on assignments with active/returned status.

#### `completion_trend_by_week: list[WeeklyTrend]`

```python
class WeeklyTrend(BaseModel):
    week_start: date
    completed_count: int
    created_count: int
```

Rolling 8-week window. Computed from `completed_at` and `created_at` timestamps.

#### `report_submission_compliance: float | None`

`report_submitted_count / total_completed_requiring_report` where applicable.
Returns `None` if no completed assignments exist (not zero).

#### `escalation_rate: float | None`

`escalated_count / total_assignments` where `total_assignments > 0`.
Returns `None` if no assignments. Not stored; computed at dashboard query time.

#### `average_revision_cycles: float | None`

Average `returned_count` per assignment for completed assignments.
Returns `None` if no completed assignments.

#### `evidence_attachment_rate: float | None`

Proportion of completed assignments that have at least one evidence attachment.
Returns `None` if no completed assignments.

#### `assignments_without_recent_report: int`

Count of ACTIVE assignments with `status=ASSIGNED` or `status=ACCEPTED` and no report
submitted in last 30 days. Computed from assignment status and `report_submitted_at` (if tracked).

#### `unit_completion_table: list[UnitCompletionEntry]`

Extends existing `by_unit`. Adds completion rate per unit.

```python
class UnitCompletionEntry(BaseModel):
    unit_id: str
    unit_name: str
    total: int
    completed: int
    overdue: int
    completion_rate: float | None
```

### Dashboard Anti-Fake Requirements

1. `fake_metrics` MUST remain `False` — no exceptions.
2. `data_source` MUST remain `"computed_from_assignments"` — no exceptions.
3. If DB query fails, raise `DataQualityError` — do not fallback to fake zeros.
4. If a new field cannot be computed (e.g. no data), return `None` or empty list — not 0 when 0 is misleading.
5. Frontend MUST render `DataQualityError` banner if `fake_metrics != false` or `data_source` mismatch.
6. No mock values in development or staging that could be committed to production.

## Section 13 — Performance Follow-Up Plan

### Problem Statement

A-031.1-RUNTIME backend test suite: **167 tests / ~2760s (~46 min) wall clock**.
Classification: **LIVE_DB_SETUP_OVERHEAD**.

Root cause (inferred): `reset_shared_state` autouse fixture + `_reset_template_state` called
2x/test; each test incurs fresh DB setup overhead even for stateless logic tests.

### Proposed Actions (SPEC ONLY — not implemented in A-031.5-SPEC)

| Action | Description | Priority |
|---|---|---|
| Module-scoped fixture pooling | Share DB setup once per test module; reset only rows, not schema | HIGH |
| Test DB snapshot restore | Use `pg_restore` or `TRUNCATE` + seed after snapshot; skip full template recreation | MEDIUM |
| Fast/slow markers | `pytest.mark.fast` for stateless logic; `pytest.mark.db` for DB-dependent | MEDIUM |
| Split pack strategy | Separate `test_a0311_rector_fast.py` vs `test_a0311_rector_db.py` | LOW |

### Constraints

- No test weakening (no `skip`, no `xfail`, no coverage reduction).
- No isolation guarantee reduction.
- Must preserve tenant isolation between test cases.
- Performance improvement target: ≤600s for 167 tests (10x improvement).

### Decision

Performance follow-up is a **quality prerequisite** before broad regression gates.
It is NOT a product feature. Implement before A-031.5-B1 gate runs if any gate includes
full A-031.1 test suite.
