Date: 2026-06-18
Action ID: A-055.0-SPEC
Status: DRAFT - SPECIFICATION ONLY

## 1. Purpose

This action defines the first safe stabilization step for the National University OS root flow.

Root flow:

```text
platform superadmin
-> create university tenant
-> create tenant admin
-> tenant appears in login directory
-> tenant admin login
-> tenant-scoped university workspace
```

This document is intentionally specification-only.
No runtime code, migrations, tests, routing, RBAC, or frontend behavior is changed by A-055.0-SPEC.

## 2. Why This Comes First

The project is already a national-scale University OS with many verticals.
Before adding more vertical branches, the root must be trusted.

If the root flow is unclear, every vertical becomes harder to validate because the team cannot confidently answer:

- who created the university tenant;
- who owns platform-level actions;
- who owns institution-level actions;
- how tenant admin enters the system;
- whether navigation is platform-scoped or tenant-scoped;
- whether a vertical is running inside the correct tenant boundary.

## 5. Current Root Gap

The backend has the pieces for full tenant + tenant admin provisioning, but the frontend root path is split:

```text
/console/platform/tenants
    platform console tab
    lists tenants
    lifecycle actions
    no full create university + tenant admin flow yet

/console/tenants
    legacy/simple tenant CRUD page
    creates tenant record only
    no tenant admin creation
```

Therefore, the canonical root flow is not yet one clean product path.

## 6. Decision For A-055 Chain

Canonical direction:

```text
/console/platform/tenants becomes the platform superadmin onboarding surface.
```

Legacy disposition:

```text
/console/tenants is not deleted in early A-055 work.
It remains a legacy/simple CRUD or tenant governance candidate until the canonical flow is proven.
```

Backend direction:

```text
Prefer one explicit full provisioning contract for platform superadmin flow.
It must create or securely initiate both:
1. university tenant
2. first tenant admin
```

Open design choice for A-055.1:

```text
Option A: adapt /platform/tenants to create tenant admin directly.
Option B: add a platform-admin wrapper around the existing self-service full provisioning logic.
Option C: keep invite mode only if invite persistence and consumption are implemented and tested.
```

Recommended default:

```text
Option B, unless closer code review shows /platform/tenants can be safely extended without duplicating logic.
```

Reason:

- `self_service_router.py` already has stronger idempotency, tenant admin creation, conflict handling, subscription creation, and retry behavior;
- platform admin flow should reuse that proven behavior rather than creating a second provisioning engine.

## 7. Role And Navigation Target

Current issue:

```text
admin and superadmin navigation are too close.
```

Desired behavior:

```text
superadmin
    sees Platform Management
    creates universities
    manages plans, quotas, provider readiness, platform ops

tenant admin
    sees University Workspace
    manages institution setup and university verticals
    does not feel like platform owner
```

No navigation rewrite should happen before the root provisioning path is selected.

## 8. Safety Rules

A-055 chain must follow these rules:

```text
1. Do not delete old tenant routes in the first implementation slice.
2. Do not rename existing vertical routes.
3. Do not change tenant isolation policy.
4. Do not weaken X-Tenant-ID checks.
5. Do not create a second provisioning engine if existing logic can be reused.
6. Do not claim production readiness.
7. Every tenant/admin creation path must be auditable.
8. Tenant admin must be tenant-scoped from first login.
9. Platform superadmin must not become a silent cross-tenant bypass.
10. All critical actions remain human-approved.
```

## 11. Definition Of Done For Root

Root flow is considered stable only when all are true:

```text
1. Platform superadmin can log in.
2. Superadmin can create a university tenant from the canonical platform surface.
3. The same action creates or securely activates the first tenant admin.
4. The tenant receives defaults: plan, subscription, role permissions, local users flag, LDAP default, backup profile, root org unit.
5. The tenant appears in the login directory.
6. Tenant admin can log in with the correct tenant context.
7. Tenant admin cannot cross into another tenant.
8. Superadmin and tenant admin see clearly different navigation/workspace intent.
9. The flow has backend tests.
10. The flow has frontend tests or E2E smoke coverage.
11. No old vertical routes are broken.
```
