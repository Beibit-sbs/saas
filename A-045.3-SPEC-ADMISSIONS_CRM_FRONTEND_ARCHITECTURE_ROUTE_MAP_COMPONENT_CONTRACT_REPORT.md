## 4 Page Inventory

### 4.1 AdmissionsOverviewPage
- purpose: module landing with status summaries, queue snapshots, and action entry points
- permissions: admissions_crm.read, admissions_crm.dashboard.read
- data source: /leads, /applicants, /applications (aggregated client-side in Batch 1), future /dashboards/*
- actions: quick navigation, open create dialogs, open workflow/audit

### 4.2 LeadRegistryPage
- purpose: searchable lead registry with status transitions and conversion entry
- permissions: admissions_crm.lead.read, admissions_crm.lead.qualify, admissions_crm.applicant.convert
- data source: /leads, /leads/{lead_id}, /leads/{lead_id}/status-history
- actions: create, qualify, convert-to-applicant, add note/tag

### 4.3 ApplicantRegistryPage
- purpose: tenant-scoped applicant directory and profile lifecycle surface
- permissions: admissions_crm.applicant.read, admissions_crm.applicant.create, admissions_crm.applicant.profile.manage
- data source: /applicants, /applicants/{applicant_id}
- actions: create applicant, inspect profile, initiate application

### 4.4 ApplicationRegistryPage
- purpose: application pipeline operations and submit transition
- permissions: admissions_crm.application.read, admissions_crm.application.create, admissions_crm.application.submit
- data source: /applications, /applications/{application_id}, /applications/{application_id}/status-history
- actions: create application, submit, inspect workflow state

### 4.5 WorkflowPage
- purpose: visualize lifecycle transitions and queue health for lead/applicant/application flows
- permissions: admissions_crm.read, admissions_crm.application.review.queue, admissions_crm.decision.review
- data source: /leads/*/status-history, /applications/*/status-history, workflow event feed
- actions: filter by stage/owner/age, open entity drilldowns

### 4.6 AuditPage
- purpose: append-only operational audit view with action/entity filters
- permissions: admissions_crm.communication.audit.read, admissions_crm.dashboard.read
- data source: audit events endpoint family (Batch 1 via workflow/audit events data source)
- actions: filter/export (export only where analytics.export permission exists)

### 4.7 AdmissionsDashboardPage
- purpose: aggregate KPI and operational cards for admissions management
- permissions: admissions_crm.dashboard.read, admissions_crm.analytics.read, admissions_crm.dashboard.executive.read
- data source: /dashboards/* and /analytics/* families (fallback to safe partial cards in Batch 1)
- actions: filter, drilldown, tenant-safe segment switch

## 6 Form Contracts

### 6.1 LeadCreateForm
- fields: lead_ref, full_name, email, phone, source_channel, metadata
- validation: required ref/name/email, max lengths aligned to backend schema, metadata object-only
- permissions: admissions_crm.lead.create or admissions_crm.create

### 6.2 LeadEditForm
- fields: full_name, email, phone, source_channel, note
- validation: immutable lead_ref, email format, note max length
- permissions: admissions_crm.lead.update

### 6.3 ApplicantCreateForm
- fields: lead_id, applicant_ref, full_name, email, metadata
- validation: lead_id required in tenant scope, ref/name/email required
- permissions: admissions_crm.applicant.create and admissions_crm.applicant.convert

### 6.4 ApplicationCreateForm
- fields: applicant_id, application_ref, program_code, intake_term, metadata
- validation: all base fields required, applicant must resolve in same tenant
- permissions: admissions_crm.application.create

### 6.5 NoteForm
- fields: entity_type, entity_id, note
- validation: note non-empty, max length policy, entity_type enum limited to lead/applicant/application
- permissions: admissions_crm.update or entity-scoped update permission

### 6.6 AssignmentForm
- fields: entity_type, entity_id, counselor_user_id, reason
- validation: counselor required, reason required for reassignment, entity must be tenant-owned
- permissions: admissions_crm.lead.assign or admissions_crm.applicant.update

## 9 UX Workflow Mapping

Primary UX journey:
- Lead -> Applicant -> Application

### 9.1 Navigation model
- leads list -> lead detail -> convert action -> applicant detail -> create application -> application detail -> submit

### 9.2 Breadcrumb contract
- Admissions / Leads / Lead Detail
- Admissions / Applicants / Applicant Detail
- Admissions / Applications / Application Detail

### 9.3 Action visibility contract
- qualify visible only in eligible lead states and with lead.qualify permission
- convert visible only after qualifying conditions and with applicant.convert permission
- submit visible only on application_started and with application.submit permission

### 9.4 Status visualization
- status badge with strict enum mapping from backend status values
- timeline panel for status-history and workflow transition events
- blocked/invalid transitions rendered as disabled actions with reason tooltip

## 10 Tenant UX Rules

Strict tenant isolation UX rules:
1. tenant context required before route resolution
2. all query hooks include tenant-safe cache keys and tenant parameter propagation
3. no global cross-tenant selectors in admissions module UI
4. drilldowns preserve current tenant scope only
5. error handling must not reveal out-of-tenant identifiers
6. filter presets are tenant-local only
7. shared dashboard exports require tenant-scoped data serialization

Tenant UX result: PASS

## 11 Anti-Fake Controls

Explicit UI prohibitions:
1. fake applicant score widgets
2. conversion probability scorecards without authoritative backend signal contract
3. fake admission decision banners
4. fake analytics values or synthetic KPI placeholders presented as real
5. fake workflow states not backed by backend enums
6. brain recommendation widgets that imply autonomous execution
7. synthetic outcomes or auto-completion overlays

Enforcement contract:
- all cards must declare data_source_type: live | unavailable | advisory
- unavailable data renders explicit "not enabled in current runtime scope" label
- decision-support banners must include human-review required marker

Anti-fake result: PASS
