### **FEATURE 1: H-1 — STUDENT INTERVENTION ORCHESTRATION (Brain Core Automation)**

**Feature:** Brain Core-driven cross-module automation of student risk interventions  
**Priority:** P0 (flagship feature, architectural foundation)  
**Score:** 34/35 (T1)

#### Why This Matters for Product Completeness

This is the **signature feature** that transforms SBS UB from a data repository into an **Autonomous University Brain**. Every other feature feeds signal into this system; the system responds with coordinated action.

**Product Completeness Contribution:**
- Realizes Brain Core → Signal → Decision → Action → Outcome loop (architectural mandate)
- Automates manual intervention workflows (advisor + finance + academic offices coordinate separately today)
- Creates feedback mechanism (outcomes inform brain model, system improves continuously)
- Establishes reusable automation framework for all future intelligent workflows

#### Business/Operational Pain

- **Today:** Student at risk? Advisor may not know. Academic signals in LMS, financial signals in billing, engagement signals scattered. Recovery is ad-hoc.
- **Pain:** By the time advisor notices, student 2-3 weeks behind. Tutoring, payment plan, intervention late. Retention lost.
- **Opportunity:** Brain Core detects day 1. Automates email + advisor notification. Advisor acts immediately. +2-3 weeks intervention advantage.

#### Modules Connected

- **university_core:** Students, enrollments, academic_records (signal source)
- **brain_core:** Anomaly detection, decision engine (intelligence)
- **billing:** Payment status, subscription tier (financial signal)
- **analytics:** KPI aggregation, outcome measurement (feedback loop)
- **audit:** All automation decisions logged (compliance + learning)
- **notifications:** Multi-channel delivery (email, SMS, in-app)
- **automation:** Workflow orchestration (execute rules safely)
- **rbac:** Permission checks (can advisor act? can system auto-suspend?)

#### Existing Pieces

✅ **Backend**
- university_core: student enrollment + academic_records tables exist
- brain_core: anomaly detection (partial), decision engine (partial)
- audit: all mutation logging works
- notifications: infrastructure exists (partial template + preference system)
- automation: basic workflow engine exists

✅ **Frontend**
- Dashboard framework exists (charts, cards, components available)
- Notification UI patterns exist (alerts, toasts)

❌ **Gaps**
- Brain Core daily batch scheduler (orchestrates analysis)
- Decision rule evaluation engine (routes by risk type: academic vs. financial vs. engagement)
- Automation workflow execution safety gate (requires manual approval for sensitive actions)
- Outcome measurement 6-week follow-up protocol

#### Trigger Event

`student.anomaly.detected` (published by Brain Core daily batch) → Routes to Decision Engine:
- **Academic risk** (GPA drop >0.5, attendance <70%, incomplete submissions): Routes to A-1 advisory workflow
- **Financial risk** (payment >7 days late, billing flag): Routes to B-2 collections workflow
- **Engagement risk** (login <2x/week, forum inactive, assignment submission late): Routes to mentorship workflow

#### Brain Core Role

**PRIMARY role** — H-1 is the orchestration layer:
1. **Signal Aggregation:** Reads signals from academic (GPA, attendance, engagement), financial (payment, billing), enrollment (progress)
2. **Anomaly Detection:** Compares to peer cohort + student baseline → flags unexpected changes
3. **Contextualization:** Is change due to known event (drop/add window, break, illness)? Or genuine risk?
4. **Decision:** Routes anomaly by type + magnitude to appropriate handler
5. **Action:** Triggers automation (safe) or escalates for manual approval (sensitive)
6. **Outcome Tracking:** Measures (after 6 weeks) — did student improve? Did intervention help? Model accuracy?
7. **Feedback Loop:** Outcomes inform next model iteration (continuous learning)

#### Workflow / Action Steps

```
Daily (01:00 UTC):
  1. Brain Core batch: read_all_students() + score_per_signals()
  2. For each student with score > threshold:
     a. Detect_anomalies(current_score vs. baseline, vs. cohort)
     b. Contextualize (known events? holidays? add/drop period?)
     c. If genuine anomaly:
        - Route by risk type (academic/financial/engagement)
        - Load_automation_policy(risk_type)
        - For each_recommended_action:
          * If action.requires_approval: escalate_to_advisor + email
          * Else: execute_action() + log_decision()
  3. Outcomes (weekly background):
     a. For each intervention (6 weeks old), measure outcome
     b. Did student improve? Yes/No → update model feedback
     c. Publish outcome event (for analytics dashboard)
```

   - Model confidence over time (improving?)


## Common Infrastructure Required

All 5 selected features depend on shared infrastructure. Implement in **A-013 Phase 0 (concurrent with feature endpoints):**

### 1. **Daily Batch Scheduler**
- **Purpose:** Orchestrate daily analysis jobs (Brain Core anomaly detection, delinquency batch, KPI recalculation)
- **Requirements:**
  - Schedule job (01:00 UTC): trigger Brain Core batch
  - Idempotent (safe to retry if failed)
  - Logging (what ran, when, status, errors)
  - Alert on failure (notify ops)
- **Implementation:** APScheduler or Celery Beat
- **Tests:** Batch runs daily; outputs consistent; retries work correctly

### 2. **Event Publishing**
- **Purpose:** Publish events from module operations (course.scheduled, enrollment.created, grade.submitted, invoice.created, payment.received, etc.)
- **Events needed for first 5 features:**
  - `course.scheduled` (triggers C-1 course publication)
  - `enrollment.created` (triggers C-1 enrollment confirmation)
  - `student.anomaly.detected` (triggers H-1 + A-1 automation)
  - `invoice.delinquent` (triggers B-2 workflow)
  - `intervention.completed` (triggers outcome measurement)
- **Implementation:** Event broker (Redis pub/sub or message queue)
- **Tests:** Event publishing doesn't block; consumers receive events in order; retry on failure

### 3. **Notification Service**
- **Purpose:** Multi-channel notifications (email, SMS, in-app, push)
- **Requirements:**
  - Template management (email templates with variables)
  - Preference system (user opts in/out of channels)
  - Delivery orchestration (queue → send via channel → retry on failure)
  - Audit logging (notification sent, when, to whom, result)
- **Channels:**
  - Email (primary)
  - SMS (for critical alerts)
  - In-app notification (all features)
  - Push notification (mobile app, if exists)
- **Implementation:** Notification service (internal or third-party: SendGrid, Twilio, OneSignal)
- **Tests:** Notifications queued correctly; delivered to correct channel; failures retried; audit logged

### 4. **Automation Workflow Engine**
- **Purpose:** Execute rules-based workflows (if risk_score > X, then [action1, action2, action3])
- **Requirements:**
  - Rule definition DSL (easy to define business rules without coding)
  - Execution engine (evaluate rules safely)
  - Safety gate (manual approval for sensitive actions)
  - Audit logging (what rule? what action? when? why?)
- **Implementation:** Rules engine (internal or third-party: Drools, easy-rules)
- **Tests:** Rules evaluate correctly; safe actions execute automatically; sensitive actions escalate to human

### 5. **Audit Data Lineage**
- **Purpose:** For every KPI, compliance metric, or decision, track source data → transformation → output
- **Requirements:**
  - Lineage capture (when KPI calculated, record source queries + transformations)
  - Audit trail immutable (can't delete or modify audit records)
  - Drill-down capability (Rector sees "enrollment: 247" → clicks → sees exact query + student list)
- **Implementation:** Audit log with metadata (query, source tables, timestamp, user)
- **Tests:** Lineage captured correctly; audit trail complete + immutable; drill-down works

### 6. **Dashboard Framework**
- **Purpose:** Reusable components for all feature dashboards
- **Shared Components:**
  - Metric card (headline number, trend, sparkline)
  - Drill-down modal (filter, sort, export)
  - Chart components (line, bar, pie, heatmap)
  - Alert banner (anomaly alerts)
  - Export to PDF
- **Implementation:** Reusable React components (in frontend/src/components/dashboard)
- **Tests:** Components render correctly; responsive design; export works

### 7. **Shared Frontend Hooks & Types**
- **Purpose:** Reusable data fetching + state management
- **Hooks:**
  - `useKPIData(metric)` (fetch KPI data, refresh hourly)
  - `useNotifications()` (fetch/subscribe to notifications)
  - `useAnomalies()` (fetch brain core anomalies)
  - `useRiskProfile(student_id)` (fetch student risk data)
- **Types:**
  - `KPIMetric` (structure for all KPI metrics)
  - `Notification` (structure for all notifications)
  - `RiskProfile` (structure for student/tenant risk)
  - `Intervention` (structure for all intervention tracking)
- **Implementation:** Frontend TypeScript hooks + type definitions
- **Tests:** Hooks fetch correctly; state updates; error handling
