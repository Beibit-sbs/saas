## Contract Domain Model

The A-054 vertical defines 12 core runtime domains:

### 1. Notification Center Domain
**Purpose:** Core orchestration platform for all notification delivery, routing, and outcome tracking.

**Canonical Owner:** `brain_core`
**Bridge Owners:** `student_success`, `academic_operations`, `executive_governance`, `analytics`
**Consumers:** All student-facing, staff-facing, and executive dashboards

**Data Entities:**
- notification_message (id, recipient_group_id, template_id, status, created_at, delivered_at, read_at)
- notification_delivery_log (id, notification_id, channel, status, attempt_count, last_error, external_ref)
- notification_outcome (id, notification_id, recipient_id, action_taken, timestamp)

**Allowed Operations:**
- read_notification (PERMISSION: notifications.read)
- mark_as_read (PERMISSION: notifications.read)
- query_delivery_status (PERMISSION: audit.read)
- archive_notification (PERMISSION: notifications.read)

**Forbidden Operations:**
- autonomous_delivery_without_policy_validation
- fake_delivery_success_claims
- direct_provider_api_calls (must route through provider_readiness boundary)
- skip_tenant_isolation
- bulk_send_without_approval_gate (for >100 recipients)

**Tenant Boundary:** Multi-tenant isolation enforced via recipient_org_id filter on all queries.

**RBAC Boundary:** Communications roles (communications.summary.read, notifications.read, etc.) required for all operations.

### 2. Announcement Registry Domain
**Purpose:** Persistent, versioned storage for institutional announcements with visibility rules.

**Canonical Owner:** `communications` module
**Bridge Owners:** `brain_core` (for timing/urgency signals), `executive_governance` (for rector announcements)
**Consumers:** Student dashboards, staff dashboards, mobile app, email digest

**Data Entities:**
- announcement (id, title, body, category, priority, visibility_scope, published_at, expires_at, created_by_user_id)
- announcement_read_tracking (id, announcement_id, recipient_id, read_at)
- announcement_revision (id, announcement_id, version, changed_fields, changed_at)

**Allowed Operations:**
- read_announcement (PERMISSION: announcements.read)
- search_by_category_and_priority (PERMISSION: announcements.read)
- track_read_status (PERMISSION: announcements.read)
- query_expiration_status (PERMISSION: announcements.read)

**Forbidden Operations:**
- create_announcement (FUTURE_GATED_WORKFLOW)
- update_announcement (FUTURE_GATED_WORKFLOW)
- delete_announcement (FUTURE_GATED_WORKFLOW)
- override_visibility_rules

**Tenant Boundary:** Multi-tenant visibility rules enforced; announcements filtered by recipient tenant and role.

**RBAC Boundary:** students.read, staff.read, admin.read with role-based visibility.

### 3. Message Template Registry Domain
**Purpose:** Parameterized, reusable message templates for consistency and audit compliance.

**Canonical Owner:** `communications` module
**Bridge Owners:** `brain_core` (for signal-driven template selection)
**Consumers:** Notification Center, Escalation workflows, Brain action proposals

**Data Entities:**
- message_template (id, key, subject_template, body_template, channel_list, priority_level, requires_approval, created_at)
- template_parameter (id, template_id, param_name, param_type, required, validation_rule)
- template_usage_audit (id, template_id, context, sent_count, avg_read_rate)

**Allowed Operations:**
- read_template_list (PERMISSION: templates.read)
- query_template_by_key (PERMISSION: templates.read)
- validate_template_parameters (PERMISSION: templates.read)
- audit_template_usage (PERMISSION: audit.read)

**Forbidden Operations:**
- create_template (FUTURE_GATED_WORKFLOW)
- update_template (FUTURE_GATED_WORKFLOW)
- delete_template (FUTURE_GATED_WORKFLOW)
- inline_message_creation_without_template

**Tenant Boundary:** Templates may be organization-specific or system-wide; scoped by owner_org_id.

**RBAC Boundary:** admin.templates.read for full access; staff.templates.read for department templates only.

### 4. Notification Preference Registry Domain
**Purpose:** Individual recipient preferences for notification channels, frequency, and quiet hours.

**Canonical Owner:** `student_success` module (for student preferences), `academic_operations` (for staff)
**Bridge Owners:** `brain_core` (for preference signals), `communications` (for delivery policy enforcement)
**Consumers:** Notification Center (to determine channel routing), Brain Core (for signal filtering)

**Data Entities:**
- preference_record (id, recipient_id, channel_enabled_map, frequency_limit, quiet_hours_start, quiet_hours_end, opt_out_categories)
- preference_change_audit (id, preference_id, changed_fields, changed_at, change_reason)
- channel_subscription (id, recipient_id, channel_type, subscription_status, verified_at, external_ref)

**Allowed Operations:**
- read_user_preferences (PERMISSION: preferences.read)
- update_own_preferences (PERMISSION: preferences.read)
- query_quiet_hours (PERMISSION: preferences.read)
- audit_preference_changes (PERMISSION: audit.read)

**Forbidden Operations:**
- override_user_preferences_without_notification
- send_to_opted_out_category
- skip_quiet_hours_enforcement_without_critical_flag

**Tenant Boundary:** Preferences scoped to recipient's tenant; no cross-tenant preference leakage.

**RBAC Boundary:** Users can update their own preferences; admins can audit but not override without policy approval.

### 5. Delivery Audit Trail Domain
**Purpose:** Complete, immutable record of notification delivery events for compliance, debugging, and accountability.

**Canonical Owner:** `analytics` module
**Bridge Owners:** `brain_core` (for outcome feedback), `communications` (for reporting)
**Consumers:** Compliance dashboards, SLA reporting, incident investigation

**Data Entities:**
- audit_event (id, notification_id, event_type, timestamp, actor_id, details_json, ipv4, user_agent)
- delivery_attempt_log (id, notification_id, recipient_id, channel, external_provider_id, external_message_id, outcome, retry_count, error_code)
- sla_metric (id, notification_id, delivery_time_ms, read_time_ms, escalation_time_ms, sla_met)

**Allowed Operations:**
- query_delivery_events (PERMISSION: audit.read)
- export_audit_trail (PERMISSION: audit.read with export confirmation)
- calculate_sla_metrics (PERMISSION: audit.read)
- search_by_recipient_id (PERMISSION: audit.read)

**Forbidden Operations:**
- delete_audit_events (immutable by design)
- modify_audit_timestamps
- hide_failed_delivery_attempts
- claim_success_for_external_delivery_without_evidence

**Tenant Boundary:** Audit records tagged with tenant_id; queries filtered by tenant.

**RBAC Boundary:** admin.audit.read for full access; department.audit.read for department-scoped events only.

### 6. Escalation Workflow Registry Domain
**Purpose:** Policy-driven escalation chains for unresolved notifications, failed deliveries, and urgent situations.

**Canonical Owner:** `communications` module
**Bridge Owners:** `brain_core` (for escalation triggers), `executive_governance` (for escalation routing)
**Consumers:** Notification Center, Incident management workflows

**Data Entities:**
- escalation_policy (id, policy_key, trigger_condition, escalation_steps, notification_required, approval_gate)
- escalation_instance (id, policy_id, trigger_event_id, current_step, created_at, resolved_at, resolution_reason)
- escalation_step (id, policy_id, step_order, target_role, target_unit, wait_time_minutes, notification_template_id)

**Allowed Operations:**
- read_escalation_policy (PERMISSION: escalations.read)
- query_active_escalations (PERMISSION: escalations.read)
- record_escalation_resolution (PERMISSION: escalations.read with approval)
- audit_escalation_history (PERMISSION: audit.read)

**Forbidden Operations:**
- create_escalation_without_policy (FUTURE_GATED_WORKFLOW)
- skip_approval_gate_for_critical_escalations
- escalate_without_notifying_recipient
- auto_escalate_more_than_3_levels_without_human_decision

**Tenant Boundary:** Escalation policies are tenant-specific; escalations scoped by tenant.

**RBAC Boundary:** escalations.read for read; escalations.approve for step execution; executive_governance.escalations.manage for policy changes.

### 7. Emergency Broadcast Registry Domain
**Purpose:** Controlled, policy-gated capability for emergency and crisis communications to large recipient groups.

**Canonical Owner:** `executive_governance` module
**Bridge Owners:** `communications` (for channel orchestration), `brain_core` (for threat assessment)
**Consumers:** Crisis management dashboards, emergency response workflows

**Data Entities:**
- emergency_broadcast_template (id, key, activation_criteria, target_group_default, message_template_id, escalation_level, requires_rector_approval)
- emergency_broadcast_instance (id, template_id, initiated_by_user_id, approval_chain, activated_at, recipients_count, outcome_summary)
- emergency_broadcast_outcome (id, broadcast_id, delivery_status, read_rate, response_count, escalation_triggered)

**Allowed Operations:**
- read_emergency_readiness (PERMISSION: emergency.read)
- query_activation_criteria (PERMISSION: emergency.read)
- audit_broadcast_history (PERMISSION: audit.read with executive oversight)
- test_broadcast_routing (PERMISSION: emergency.read with simulation flag)

**Forbidden Operations:**
- activate_broadcast_without_rector_approval (requires multi-level approval chain)
- send_fake_emergency_notice
- bypass_notification_preferences_without_critical_flag
- target_group_override_without_documented_reason

**Tenant Boundary:** Emergency broadcasts are organization-wide; routing enforced by central security policy.

**RBAC Boundary:** rector.emergency_broadcast.activate for activation; director.emergency.read for query; all users have emergency.read for readiness check.

### 8. Recipient Group Registry Domain
**Purpose:** Reusable, dynamic recipient groups for broadcast messaging, filtering, and targeting.

**Canonical Owner:** `analytics` module
**Bridge Owners:** `brain_core` (for signal-driven group updates), `student_success` / `academic_operations` (for source data)
**Consumers:** Notification Center, Escalation workflows, Emergency broadcasts

**Data Entities:**
- recipient_group (id, group_key, group_type, filter_definition_json, dynamic_refresh_enabled, last_refresh_at)
- recipient_group_member (id, group_id, recipient_id, added_at, source_context)
- group_size_metric (id, group_id, timestamp, member_count, stale_percentage)

**Allowed Operations:**
- read_group_definition (PERMISSION: recipients.read)
- query_group_members (PERMISSION: recipients.read with query limit)
- get_group_size_estimate (PERMISSION: recipients.read)
- audit_group_refresh_history (PERMISSION: audit.read)

**Forbidden Operations:**
- create_group (FUTURE_GATED_WORKFLOW)
- update_filter_definition (FUTURE_GATED_WORKFLOW)
- delete_group (FUTURE_GATED_WORKFLOW)
- target_arbitrary_group_without_definition

**Tenant Boundary:** Groups scoped by tenant; members filtered by recipient tenant.

**RBAC Boundary:** analytics.recipients.read for full access; department.recipients.read for department groups only.

### 9. Communication Campaign Registry Domain
**Purpose:** Planned, trackable communication campaigns with messaging goals and outcome measurement.

**Canonical Owner:** `communications` module
**Bridge Owners:** `brain_core` (for signal-driven campaign triggering), `analytics` (for outcome measurement)
**Consumers:** Campaign dashboards, ROI reporting, Brain outcome feedback

**Data Entities:**
- campaign (id, campaign_key, campaign_type, objective, target_group_id, start_date, end_date, budget_message_count, approval_status)
- campaign_message (id, campaign_id, message_number, template_id, scheduled_send_time, recipient_group_id, sent_count)
- campaign_metric (id, campaign_id, delivery_count, read_count, engagement_count, read_rate, roi_estimate)

**Allowed Operations:**
- read_campaign_definition (PERMISSION: campaigns.read)
- query_campaign_metrics (PERMISSION: campaigns.read)
- estimate_campaign_roi (PERMISSION: campaigns.read)
- audit_campaign_changes (PERMISSION: audit.read)

**Forbidden Operations:**
- create_campaign (FUTURE_GATED_WORKFLOW)
- update_campaign (FUTURE_GATED_WORKFLOW)
- delete_campaign (FUTURE_GATED_WORKFLOW)
- claim_engagement_without_verified_read_status

**Tenant Boundary:** Campaigns scoped by organization; reporting filtered by tenant.

**RBAC Boundary:** communications.campaigns.read for view; communications.campaigns.manage for approval (future); director.campaigns.read for executive view.

### 10. Provider Readiness Registry Domain
**Purpose:** Inventory and readiness status of external communication providers (email, SMS, push, Telegram) without claiming live delivery.

**Canonical Owner:** `integration` / `provider_readiness` module
**Bridge Owners:** `communications` (for contract enforcement), `brain_core` (for capacity signals)
**Consumers:** Notification Center (for routing decisions based on readiness), Escalation workflows

**Data Entities:**
- provider_config (id, provider_key, provider_type, integration_status, credential_status, rate_limit, queue_depth)
- provider_readiness_check (id, provider_id, check_timestamp, availability_status, latency_ms, error_rate)
- provider_contract (id, provider_key, sla_claim, delivery_guarantee, support_level, contract_status)

**Allowed Operations:**
- read_provider_readiness (PERMISSION: providers.read)
- query_provider_availability (PERMISSION: providers.read)
- check_rate_limit_status (PERMISSION: providers.read)
- audit_provider_connection_history (PERMISSION: audit.read)

**Forbidden Operations:**
- activate_provider_without_credential_verification
- claim_sla_compliance_without_evidence
- send_real_messages_in_readiness_mode
- override_rate_limits_without_approval

**Tenant Boundary:** Provider configs are system-wide; rate limits enforced per tenant.

**RBAC Boundary:** admin.providers.read for full access; integration.providers.read for read-only status.

### 11. Brain Communication Action Registry Domain
**Purpose:** Bridge between Brain Core decision engine and communications execution layer.

**Canonical Owner:** `brain_core` module
**Bridge Owners:** `communications` (for message execution), `student_success` / `academic_operations` (for source signals)
**Consumers:** Notification Center (for sending), Escalation workflows, Campaign tracking

**Data Entities:**
- communication_action_proposal (id, source_signal_id, brain_signal_type, recommended_action, recommended_template_id, target_group_id, urgency_level, approval_required)
- communication_action_execution (id, proposal_id, executed_at, executed_by_actor, execution_status, notification_id, outcome_recorded)
- action_outcome_feedback (id, execution_id, outcome_type, recipient_response, timestamp)

**Allowed Operations:**
- read_action_proposals (PERMISSION: brain_actions.read)
- query_proposals_by_signal_type (PERMISSION: brain_actions.read)
- record_action_execution (PERMISSION: brain_actions.read with execution context)
- record_outcome_feedback (PERMISSION: brain_actions.read)
- audit_action_history (PERMISSION: audit.read)

**Forbidden Operations:**
- auto_execute_action_without_template_validation
- skip_policy_validation_for_urgent_signals
- claim_action_success_without_delivery_verification
- execute_action_outside_approval_scope

**Tenant Boundary:** Actions scoped by tenant; proposals filtered by recipient tenant context.

**RBAC Boundary:** brain_core.actions.read for proposal access; brain_core.actions.execute for execution (future); audit.brain_actions for outcome tracking.

**Purpose:** Specialized interface for student-parent-staff communication with moderation and boundary protection.

**Canonical Owner:** `communications` module

**Consumers:** Parent dashboards, student communication UI, academic staff interface

**Data Entities:**
- parent_communication_thread (id, student_id, parent_id, subject, created_at, last_activity_at, status)
- community_message (id, thread_id, sender_id, message_body, attachments_count, moderation_status, flagged_for_review)

**Allowed Operations:**

- query_community_sentiment (PERMISSION: analytics.sentiment.read)

**Forbidden Operations:**

**RBAC Boundary:** parents.read for parent-only view; staff.parent_communication.read for academic staff view; moderators.review for moderation access.

```

```

```
Query Parameters:
  - recipient_id: optional, string
  - status: optional, enum [pending, delivered, failed, archived]
  - date_from: optional, ISO8601

  - offset: int

Response: {
  notifications: [
    {
      id: uuid,
      recipient_id: uuid,
      template_id: uuid,
      status: enum,
      created_at: ISO8601,

      read_at: ISO8601 | null,
      delivery_log_entries: int,

  page_info: {limit, offset}
}
PERMISSION: communications.notifications.read
```

## Provider / Live-Delivery Boundary

### Strict Anti-Fake Boundaries

1. **No Real Delivery Without Verification**
   - External provider connections (email, SMS, push, Telegram) marked `integration_status: not_configured` until credentials verified.
   - No `provider_connected: true` flag without:
     - Credentials stored in secure vault
     - Health check passed
     - Rate limits obtained
     - Test message sent successfully

2. **No Fake Delivery Claims**
   - `delivery_success: true` only if:
     - external_message_id returned from provider
     - delivery_attempt_log recorded with provider response code
     - outcome verified by provider health check
   - Failed deliveries never marked as success
   - Internal queuing/staging never claimed as external delivery

3. **Provider Readiness Registry Boundaries**
   - Provider status fields are purely informational:
     - `availability: enum [available, degraded, unavailable]`
     - `latency_ms: int | null` (null if unavailable)
     - `error_rate_percent: float`
   - Status never claims:
     - "SLA compliance" without contract verification
     - "Guaranteed delivery" without proof
     - "Production readiness" without explicit authorization
   - All provider claims explicitly scoped to "readiness" status, not live operation

4. **Future Integration Contracts**
   - Email provider integration (future: A-054.5+)
   - SMS provider integration (future: A-054.5+)
   - Push notification provider integration (future: A-054.5+)
   - Telegram integration (future: A-054.5+)
   - Each requires separate A-054.X action with:
     - Provider credential handling spec
     - Rate limit enforcement spec
     - SLA monitoring spec
     - Failure recovery spec
     - Audit trail spec
     - Test mode vs. production mode spec

5. **Notification Center Delivery Routing**
   - Notification Center never sends directly to provider
   - Routing decision tree:
     - Check provider_readiness status
     - If `available`: queue to provider worker (future)
     - If `degraded`: queue to fallback channel (future)
     - If `unavailable`: queue to escalation workflow
   - Delivery_attempt_log entries never fabricated
   - All delivery attempts logged with external_provider_id or escalation_reason

6. **Audit Immutability for Delivery Claims**
   - delivery_attempt_log is append-only
   - Cannot delete, modify, or backdate entries
   - All provider responses logged exactly as received
   - Error codes preserved verbatim
   - No "success" retroactively added to failed attempts

## Brain Signal / Action Contract

### Inbound Signal Types (Triggers)
Communications actions can be triggered by Brain Core signals in these categories:

**Student Success Signals:**
- academic_risk_detected (trigger: escalation to advisor notification)
- low_attendance_risk (trigger: parent notification + counselor escalation)
- course_failure_risk (trigger: advisor notification + student support notification)
- graduation_at_risk (trigger: advisor notification + dean escalation)

**Academic Operations Signals:**
- exam_proctoring_violation_detected (trigger: student notification + academic integrity escalation)
- internship_placement_risk (trigger: student notification + career services escalation)
- research_supervision_incomplete (trigger: supervisor notification + admin escalation)

**Administrative Signals:**
- late_fee_accumulation (trigger: student + parent notification + finance escalation)
- scholarship_eligibility_change (trigger: student notification + financial aid escalation)
- compliance_gap_detected (trigger: rector notification + compliance escalation)

**Crisis Signals:**
- emergency_situation_alert (trigger: emergency broadcast activation)
- severe_incident_report (trigger: rector + security + medical escalation)
- campus_safety_threat (trigger: emergency notification + rector escalation)

### Outbound Action Proposals
Brain Core proposes communication actions with these attributes:

```
{
  source_signal_id: uuid,
  source_signal_type: string,
  recommended_action: enum [
    notify_student,
    notify_parent,
    notify_staff,
    escalate_to_director,
    escalate_to_rector,
    send_announcement,
    activate_emergency_broadcast,
    trigger_campaign
  ],
  recommended_template_id: uuid,
  target_group_id: uuid,
  recipients_count: int,
  urgency_level: enum [low, medium, high, critical],
  requires_approval: bool (true for high/critical or large groups),
  policy_validation_result: enum [compliant, needs_review, violates_policy],
  approval_chain: [role_required_list],
  human_approval_gate: bool
}
```

### Policy Validation Gates

1. **Template Compliance Gate**
   - Action must reference valid message_template_id
   - Template parameters must be satisfied
   - Template must be in active status
   - Template channel list must match available providers

2. **Recipient Validation Gate**
   - Target group must be defined and verified
   - No arbitrary recipient targeting
   - Group members must be within action scope (e.g., can't notify unrelated families)
   - Recipient preferences honored (quiet hours, opt-out categories)

3. **Escalation Gate (for high/critical urgency)**
   - Requires human approval before execution
   - Approval chain automatically routed based on urgency and scope
   - Approver roles: staff_member → director → rector (for critical)
   - Approval deadline: 15 minutes for critical signals

4. **Emergency Broadcast Gate (for emergency actions)**
   - Requires rector-level approval
   - Multi-level approval chain: director → rector
   - Activation logged with approver ID and approval reason
   - Test mode available before activation

5. **Bulk Notification Gate (for >100 recipients)**
   - Requires explicit approval
   - ROI estimate must be reviewed (campaigns)
   - Rate limit impact must be checked

### Action Execution Process
1. Brain Core proposes action with full validation result
2. Proposal stored in communication_action_proposal table
3. If approval_required: route to approval_chain, wait for human decision
4. On approval: Notification Center executes via send workflow (future)
5. Execution logged in communication_action_execution table
6. Outcome feedback collected and returned to Brain Core

### Outcome Feedback Loop
After message delivery/read/escalation/response:
1. Notification Center records outcome in notification_outcome table
2. Outcome fed back to Brain Core via action_outcome_feedback
3. Feedback includes: recipient_response, timestamp, engagement_metrics
4. Brain Core uses feedback to:
   - Improve signal timing and urgency scoring
   - Refine template effectiveness
   - Adjust recipient group targeting
   - Update policy validation rules

### No-Autonomous-Critical-Broadcast Rule
- Emergency broadcasts require explicit rector approval
- Cannot be auto-triggered by Brain signal alone
- Manual approval mandatory before activation
- Test mode available for validation without sending
- All emergency activations logged with approval metadata
